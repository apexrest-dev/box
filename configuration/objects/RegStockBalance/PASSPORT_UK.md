# Паспорт регістру залишків «Товари на складах»

## 0. Стан паспорта

- Статус: `AGREED`.
- Погодження: користувач явно погодив паспорт 2026-11-03.
- Вид: накопичувальний регістр залишків.
- Технічне ім'я: `RegStockBalance`.
- Розділ основного меню: `Звіти`.
- Реєстратор першої ревізії: `DocGoodsReceipt`.

## БЛОК A. СТРУКТУРА

### 1. Ідентичність і призначення

Клас руху `StockBalanceMovement`, таблиця `reg_stock_balance_movement`, API
`/api/v1/registers/stock-balances`. Джерело істини — незмінні рухи документів.
Регістр відповідає за кількісний залишок товару в розрізі складу.

### 2. Структура руху

| Поле | Роль | Тип | Точність | Джерело | Посилання/БД |
|---|---|---|---|---|---|
| `id` | системне | UUID | — | server | PK |
| `period` | системне | Instant UTC | seconds | документ | index |
| `recorderId/type` | системне | UUID/String | — | документ | index |
| `lineNumber` | системне | int | — | рядок | unique з recorder |
| `warehouseId` | вимір | UUID | — | шапка | `RefWarehouse`, FK |
| `productId` | вимір | UUID | — | рядок | `RefProduct`, FK |
| `quantity` | ресурс | BigDecimal | 19,3 | рядок | signed |

Ключ поточного підсумку: `warehouseId + productId`. Унікальність руху:
`recorderType + recorderId + lineNumber`.

### 3. Правила залишку

- модель рухів — signed resource;
- оборот за `[from,to)` — сума `quantity` у межах періоду;
- залишок на `at` — сума рухів із `period <= at`;
- від'ємний залишок заборонений;
- поточні підсумки увімкнені;
- знімок — на кінець календарного місяця під час закриття;
- зміна минулого періоду інвалідує пізніші знімки та запускає перерахунок від
  першого зміненого місяця;
- вартісна оцінка і собівартість у `r1` відсутні.

## БЛОК B. UI

### 4. Форма списку

Єдина read-only форма з режимами `Рухи`, `Обороти`, `Залишки`; колонки: період,
реєстратор, склад, товар, кількість. Фільтри: період, склад, товар. Подвійне
натискання реєстратора відкриває документ. Прямих create/update/delete немає.

### 5. Події введення

Поля руху — `disabled`. Фільтри мають лише локальний стандартний lifecycle і
формують типізований query, не змінюючи регістр.

## БЛОК C. БІЗНЕС-ЛОГІКА

### 6. Розрахунки

`balance = snapshot + SUM(quantity after snapshot through at)`, scale 3,
`HALF_UP`. Приклад: надходження 10,500 і 2,250 дають залишок 12,750.
Повторне проведення не додає рухи, а атомарно замінює набір реєстратора.

### 7. Формування, зберігання й API

`DocGoodsReceipt`: `warehouseId <- header.warehouseId`, `productId <- goods.productId`,
`quantity <- +goods.quantity`. Скасування проведення видаляє набір рухів.
Таблиці поточних підсумків і місячних знімків є похідними. API: movements,
turnovers, balances, rebuild. Права: `read`; службовий запис доступний лише
application-сценарію проведення.

### 8. Тести й готовність

Сума рухів, межі періоду, заборона мінуса, repeat/unpost, rebuild, SQLite і
PostgreSQL, конкурентне проведення, read-only API та UI.

## Доповнення r5 (F-NSI-10, APE-63, `PROPOSED`)

Нові необов'язкові виміри `characteristicId` (`RefProductCharacteristic`) і `seriesId`
(`RefProductSeries`) — також у `RegStockReserve` і `RegStockCost`. Заповнюються тригером з рядка
документа-реєстратора; для товарів з ознаками в `RegStockBalance` обов'язкові, видаткові рухи
контролюють залишок за ключем склад × товар × характеристика × серія. Підсумки й знімки
(`reg_stock_balance_tot` / `_snap`) лишаються в розрізі склад × товар; залишки за серіями —
`v_series_stock_balance`, звіт 510.
