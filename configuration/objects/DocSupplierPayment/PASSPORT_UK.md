# Паспорт документа «Оплата постачальнику»

## 0. Стан паспорта

- Статус: `AGREED` для ревізії `r1` (користувач погодив 2026-11-03); ревізія `r4` (розділ R4 нижче) —
  `PROPOSED`: підготовлено й реалізовано 2026-11-08 (Linear APE-56, F-PUR-05) без формального погодження.
- Ревізія: `r4` (поверх `r1`).
- Розділ основного меню: `Документи`; панелі функцій `Закупівлі` і `Фінанси` (група «Банк», важливе).
- Залежності: `RefCounterparty`, `RefOrganization`, `RefContract`, `RefBankAccount`, `RefCashDesk`,
  `DocSupplierOrder`, `DocGoodsReceipt`, `RegCounterpartySettlement`, `RegCashBalance`, `DocBankStatement`.
- Аналог у 1С:УТ 11: Документ.СписаниеБезналичныхДенежныхСредств (вид «Оплата постачальнику») /
  РасходныйКассовыйОрдер; друк — «Платіжне доручення».
- Обмеження `r1` (знято в `r4`): рух каси/банку не формувався.

## БЛОК A. СТРУКТУРА

### 1. Ідентичність і призначення

Технічне ім'я `DocSupplierPayment`, клас/ID `SupplierPayment/SupplierPaymentId`,
таблиця `doc_supplier_payment`, API `/api/v1/documents/supplier-payments`.

### 2. Поля шапки

| Поле | Назва | Тип | Розмір | Обов'язкове | Редагування | Посилання/БД |
|---|---|---|---|---|---|---|
| `id` | ID | UUID | — | так | ні | PK |
| `number` | Номер | String | 9 | так | DRAFT | UNIQUE |
| `occurredAt` | Дата | Instant | seconds | так | DRAFT | index |
| `supplierId` | Постачальник | UUID | — | так | DRAFT | `RefCounterparty`, FK |
| `currencyCode` | Валюта | String | 3 | так | у r1 read-only | `UAH` |
| `amount` | Сума оплати | BigDecimal | 19,2 | так | DRAFT | > 0 |
| `comment` | Коментар | String | 1000 | ні | DRAFT | — |
| `status` | Статус | enum | — | так | командами | DRAFT/POSTED |
| `version` і аудит | Службові | — | — | так | ні | optimistic/audit |

Табличних частин немає.

### 3. Дочірні структури

Відсутні. Рознесення оплати за конкретними накладними не входить у `r1`.

### 4. Статуси й життєвий цикл

`DRAFT -> POSTED -> DRAFT` командами post/unpost. Проведений документ read-only і
не видаляється фізично. F9 копіює тільки бізнес-реквізити в нову чернетку.

## БЛОК B. UI

### 5. Форми

Список, документ і вибір. Форма:

```text
HEADER
  actions: Провести і закрити | Записати | Провести | Скасувати проведення
  number[20] | occurredAt[20]
  supplier[60] | currency[15] | amount[25]
FOOTER
  comment[100]
```

### 6. Події введення

`number`, `occurredAt`, `supplier`, `amount`, `comment` — стандартні події з
типізованими командами зміни реквізиту. `currencyCode` у `r1` disabled.

## БЛОК C. БІЗНЕС-ЛОГІКА

### 7. Обов'язкові сценарії

`InitializeSupplierPayment`, `SaveSupplierPayment`, `PostSupplierPayment`,
`UnpostSupplierPayment`, `CopySupplierPayment`. Сервер перевіряє права, статус,
версію, активність контрагента й позитивну суму.

### 8. Розрахунки

Розрахункових полів немає. `amount` нормалізується до scale 2 з `HALF_UP`.
Приклад: введене `500` зберігається як `500,00`.

### 9. Проведення й регістр

Один рух `RegCounterpartySettlement`:

```text
period <- occurredAt
counterpartyId <- supplierId
direction <- PAYABLE
currencyCode <- currencyCode
amount <- -amount
```

Перед записом сервер у тій самій транзакції перевіряє, що залишок `PAYABLE` не
стане від'ємним. Repeat замінює рух; unpost видаляє його.

### 10. Зберігання й API

Одна таблиця документа, міграції двох СУБД, list/get/initialize/create/update/
post/unpost/copy API. Права `read/create/update/post/unpost`; повний аудит.

### 11. Тести й готовність

Позитивна сума, заборона переплати, статуси, повтор/unpost, конкурентна оплата,
SQLite/PostgreSQL, API/права/аудит та сценарій часткового/повного погашення.


## R4. ДЖЕРЕЛО КОШТІВ, ДОГОВІР, ЗАМОВЛЕННЯ, ПЛАТІЖНА ІНСТРУКЦІЯ (F-PUR-05, `PROPOSED`)

### R4.1. Нові поля шапки (`db/31_r4_supplier_payment.sql`)

| Поле | Назва | Тип | Обов'язкове | Правило |
|---|---|---|---|---|
| `organizationId` | Організація | UUID | так | з r4 F-NSI-09; документ на підставі — організація підстави |
| `paymentForm` | Форма оплати | enum `BANK` / `CASH` | так | за замовчуванням `BANK` |
| `bankAccountId` | Банківський рахунок | `RefBankAccount` | для `BANK` | порожній → основний гривневий рахунок організації; лише UAH, тієї ж організації |
| `cashDeskId` | Каса | `RefCashDesk` | для `CASH` | порожня → перша гривнева каса організації; лише UAH, тієї ж організації |
| `contractId` | Договір | `RefContract` (`WITH_SUPPLIER`) | ні | порожній → договір замовлення / підстави або єдиний діючий договір постачальника |
| `supplierOrderId` | Замовлення постачальнику | `DocSupplierOrder` | ні | лише проведене, той самий постачальник і організація |
| `baseDocType` / `baseDocId` | Документ-підстава | `DocGoodsReceipt` / `DocSupplierOrder` | ні | заповнюється введенням на підставі |
| `purpose` | Призначення платежу | String 500 | так (авто) | порожнє → «Оплата за товар згідно з <підстава>, <договір>» |
| `recipientIban` | IBAN отримувача | String 34 | ні | порожній → IBAN з картки постачальника; перевірка mod 97 |

Для `BANK` каса очищується, для `CASH` — рахунок і IBAN отримувача. Валюта — лише UAH (розрахунки з
контрагентами ведуться в гривні).

### R4.2. Проведення

```text
RegCashBalance:            period = occurredAt, місце = bankAccountId | cashDeskId, amount = −amount,
                           operation_kind = SUPPLIER_PAYMENT
RegCounterpartySettlement: counterparty = supplierId, direction = PAYABLE, amount = −amount, organization
```

Контроль у транзакції: від'ємний залишок рахунку / каси (`BANK_BALANCE_NEGATIVE` / `CASH_BALANCE_NEGATIVE`
на будь-який момент), переплата постачальнику в розрізі організації (`SETTLEMENT_NEGATIVE_BY_ORGANIZATION`;
авансів ще немає). Повторне проведення замінює рухи, скасування видаляє. API r1 `trade_doc.*_supplier_payment`
делегує в `trade_pay_doc`.

### R4.3. Правило одного платежу (без подвійного обліку)

Кожен фактичний платіж рухає кошти й взаєморозрахунки **рівно одним первинним документом**: ВКО / ПКО,
`DocSupplierPayment` / `DocCustomerPayment` (APE-57) або **неприв'язаний** рядок `DocBankStatement`.

- Рядок виписки «Оплата постачальнику» може посилатися на безготівкову оплату (`paymentDocId`); такий рядок
  лише звіряє (рахунок, контрагент, сума мають збігатися) і рухів не пише — як рядки готівки з касовими ордерами.
- Проведення виписки автоматично прив'язує неприв'язані рядки до проведених безготівкових оплат того ж рахунку,
  постачальника й суми в межах ±3 днів (спершу — збіг номера платіжки з номером оплати); команда «Підібрати оплати».
- Прив'язана оплата має бути проведена (`BANK_PAYMENT_NOT_POSTED`); одна оплата — не більше одного рядка.
- Оплату, яку вже відобразив неприв'язаний рядок проведеної виписки, провести не можна
  (`PAYMENT_ALREADY_IN_STATEMENT`): скасуйте виписку, проведіть оплату, проведіть виписку — рядок прив'яжеться.
- Оплату, прив'язану до проведеної виписки, не можна скасувати, до будь-якої — видалити (`PAYMENT_LINKED_TO_STATEMENT`).
- Готівкова оплата постачальнику — або ВКО «Оплата постачальнику», або `DocSupplierPayment` з формою `CASH`
  (обидва — первинні касові документи; один платіж оформлюють одним із них).

### R4.4. Введення на підставі

| Звідки | Команда | Сума |
|---|---|---|
| Прибуткова накладна (проведена) | «Створити оплату постачальнику» | min(сума накладної, кредиторка організації) |
| Замовлення постачальнику (проведене) | «Створити оплату постачальнику» | min(сума замовлення − сплачено за замовленням, кредиторка) |

Нульова сума → `PAYMENT_NOTHING_TO_PAY`. Форма — `BANK`, якщо в організації є гривневий рахунок, інакше `CASH`.

### R4.5. Друковані форми (`trade_print.document_html`)

- `PAYMENT_ORDER` «Платіжна інструкція (платіжне доручення)» — для `BANK`: платник (організація, ЄДРПОУ, IBAN,
  банк, МФО), отримувач (найменування, ЄДРПОУ, IBAN), сума цифрами й прописом, призначення, підписи, «Проведено банком».
- `PAY_KO2` «Видатковий касовий ордер (КО-2)» — для `CASH`.
