# Паспорт довідника «Одиниці виміру»

## 0. Стан паспорта

- Статус: `AGREED`.
- Ревізія: `r1`.
- Погодження: користувач погодив перехід до реалізації командою «Далі» 2026-11-03.
- Пов'язані ADR: `docs/adr/0001-platform-and-module-structure.md`, `docs/adr/0002-database-and-migrations.md`, `docs/adr/0003-javafx-client-and-api-boundary.md`.
- Залежні паспорти: немає.

## БЛОК A. СТРУКТУРА

### 1. Ідентичність і призначення

| Параметр | Значення |
|---|---|
| Українська назва | Одиниці виміру |
| Технічне ім'я об'єкта | `RefUnitOfMeasure` |
| Доменний клас | `UnitOfMeasure` |
| Тип ID | `UnitOfMeasureId` |
| Таблиця БД | `ref_unit_of_measure` |
| DTO елемента | `UnitOfMeasureDto` |
| DTO рядка списку | `UnitOfMeasureListItemDto` |
| Базовий API | `/api/v1/catalogs/unit-of-measures` |
| Розділ інтерфейсу | Довідники |

Довідник зберігає одиниці виміру товарів і послуг: повне найменування,
скорочене позначення та ознаку дозволу дробової кількості.

- Вид: простий, неієрархічний довідник.
- Групи: не підтримуються.
- Власник: відсутній.
- Код: текстовий, максимальна довжина 9, унікальний, автоматично пропонується зі збереженням початкових нулів і може бути змінений вручну.
- Вид видалення: `MARK_FOR_DELETION` — помітка на видалення без фізичного видалення запису.

### 2. Поля

| Поле Java / ім'я метаданих | Назва | Тип | Розмір/точність | Обов'язкове | Default | Редагованість | Посилання | БД/API/індекс |
|---|---|---|---|---|---|---|---|---|
| `id` | ID | UUID | — | так | application generated | ні | — | `id`, PK |
| `code` | Код | String | до 9 | так | server sequence | так | — | `code`, UNIQUE |
| `name` | Найменування | String | 255 | так | — | так | — | `name`, index |
| `shortName` / `ShortName` | Скорочене найменування | String | 20 | так | — | так | — | `short_name` |
| `fractional` / `Fractional` | Дозволити дробову кількість | Boolean | — | так | `false` | так | — | `fractional` |
| `state` | Стан | `CatalogState` | — | так | `ACTIVE` | лише командами | — | `state`, index |
| `version` | Версія | Long | — | так | `0` | ні | — | `version`, optimistic lock |
| `createdAt` | Створено | Instant | UTC | так | server clock | ні | — | `created_at` |
| `createdBy` | Автор створення | UUID | — | так | current user | ні | користувач | `created_by` |
| `updatedAt` | Змінено | Instant | UTC | так | server clock | ні | — | `updated_at` |
| `updatedBy` | Автор зміни | UUID | — | так | current user | ні | користувач | `updated_by` |

`name` і `shortName` перед перевіркою обрізаються по краях. Порожнє після
обрізання значення заборонене. Унікальність скороченого найменування в першій
версії не встановлюється: стабільним унікальним ідентифікатором для оператора є
код, а для API — UUID.

### 3. Ієрархія, власник і дочірні структури

- Полів `parent` і `owner` немає.
- Табличних частин і дочірніх сутностей немає.
- `QueryTable` та `OwnedCatalogTable` у формах першої версії не використовуються.

### 4. Стани, інваріанти та команди

Стани:

- `ACTIVE` — елемент доступний для нового вибору;
- `MARKED_FOR_DELETION` — елемент збережений для історії, але за замовчуванням
  не пропонується в новому виборі.

Інваріанти:

- автоматично сформований код складається з 9 десяткових цифр;
- вручну введений код містить від 1 до 9 символів;
- сервер формує наступний код послідовно: `000000001`, `000000002`, ...;
- видані коди не перевикористовуються;
- `name` має довжину 1–255 символів після обрізання;
- `shortName` має довжину 1–20 символів після обрізання;
- помічений на видалення елемент не можна вибрати для нового посилання;
- історичні посилання на помічений елемент залишаються чинними й відображуваними;
- фізичне видалення через API або UI відсутнє.

Типізовані команди:

- `InitializeUnitOfMeasure` — отримати початковий стан нового елемента;
- `CreateUnitOfMeasure` — створити елемент;
- `UpdateUnitOfMeasure` — змінити найменування, скорочене найменування або
  ознаку дробової кількості;
- `MarkUnitOfMeasureForDeletion` — встановити помітку на видалення;
- `RestoreUnitOfMeasure` — повернути елемент у стан `ACTIVE`.

## БЛОК B. UI

### 5. Форми

Використовуються три форми: форма списку, форма елемента і форма вибору.
Автогенерація форм не застосовується; форми реалізуються Java-кодом на базі
спільної JavaFX-бібліотеки.

#### 5.1. Форма списку

- Правило списку: `docs/ui/LIST_SIMPLE_CATALOG_UK.md`.
- Відкривається з пункту «Одиниці виміру» розділу «Довідники».
- Колонки: `code[15] | name[45] | shortName[25] | fractional[15]`.
- Початкове сортування: `name ASC`, потім `code ASC`.
- Початковий фокус: таблиця списку.
- Команди: створити, відкрити, помітити на видалення, відновити, оновити.
- Стандартні клавіші: `Insert` — створити, `F2` — відкрити, `F3` — пошук,
  `Delete` — помітити на видалення з підтвердженням, `F9` — створити копію як
  новий елемент без ID, коду, версії й аудиту.

#### 5.2. Форма елемента

```text
FORM unitOfMeasureEditor

HEADER
  @save | @saveAndClose

CONTENT
  code[20] | name[*]
  shortName[50] | fractional
```

- Початковий фокус нового елемента: `name`.
- для нового елемента `code` спочатку порожній; оператор може ввести його вручну,
  а якщо залишить порожнім, сервер атомарно призначить наступний код під час запису;
- `name` і `shortName` використовують стандартний `TextField`.
- `fractional` використовує стандартний прапорець.
- Закриття зміненої форми вимагає вибору: записати, не записувати або скасувати
  закриття.

#### 5.3. Форма вибору

- Правило вибору: `docs/ui/REFERENCE_PICKER_UK.md`.
- Колонки: `code[20] | name[55] | shortName[25]`.
- За замовчуванням показує лише `ACTIVE`.
- Контекстний пошук виконується за `name`, `shortName` і `code`.
- Подвійний клік або `Enter` підтверджує вибір; `Esc` скасовує його.
- Створення нового елемента доступне лише за наявності права `create`.

### 6. Події введення реквізитів

| Реквізит | Компонент | Початок введення | Завершення введення | Типізований запит/команда | Серверна реакція |
|---|---|---|---|---|---|
| `code` | TextField | standard | standard | входить у `CreateUnitOfMeasure` або `UpdateUnitOfMeasure` | Перевірка формату, довжини й унікальності під час запису |
| `name` | TextField | standard | standard | входить у `CreateUnitOfMeasure` або `UpdateUnitOfMeasure` | Нормалізація, повна валідація під час запису |
| `shortName` | TextField | standard | standard | входить у `CreateUnitOfMeasure` або `UpdateUnitOfMeasure` | Нормалізація, повна валідація під час запису |
| `fractional` | CheckBox | standard | standard | входить у `CreateUnitOfMeasure` або `UpdateUnitOfMeasure` | Повна валідація під час запису |

Зміна поля не надсилає запит на кожен символ. UI накопичує локальний стан форми,
а сервер приймає лише типізовану команду запису.

## БЛОК C. БІЗНЕС-ЛОГІКА

### 7. Обов'язкові сценарії довідника

#### 7.1. Початок введення нового елемента

- Запит: `InitializeUnitOfMeasure`.
- Право: `catalog.unit-of-measure.create`.
- Транзакція запису не відкривається, дані не зберігаються.
- Сервер повертає DTO без `id` і `code`, зі `fractional=false`, початковою
  версією та capabilities форми.

#### 7.2. Створення

- Команда: `CreateUnitOfMeasure(code, name, shortName, fractional, idempotencyKey)`.
- Право: `catalog.unit-of-measure.create`.
- В одній транзакції сервер перевіряє інваріанти й ручний код або, якщо він
  порожній, виділяє наступний автоматичний код,
  створює ID, записує аудит і повертає актуальний `UnitOfMeasureDto`.
- Повтор команди з тим самим `idempotencyKey` не створює дубль.

#### 7.3. Зміна

- Команда: `UpdateUnitOfMeasure(id, code, name, shortName, fractional, expectedVersion)`.
- Право: `catalog.unit-of-measure.update`.
- В одній транзакції сервер перевіряє інваріанти й `expectedVersion`, змінює
  дозволені поля, оновлює аудит і повертає актуальний DTO.
- Конфлікт версії повертає стабільну помилку `OPTIMISTIC_LOCK_CONFLICT`.

#### 7.4. Помітка на видалення та відновлення

- Команди: `MarkUnitOfMeasureForDeletion(id, expectedVersion)` і
  `RestoreUnitOfMeasure(id, expectedVersion)`.
- Право: `catalog.unit-of-measure.delete`.
- Обидві команди виконуються транзакційно, змінюють лише стан, версію та аудит.
- Існуючі історичні посилання не блокують помітку на видалення.

### 8. Розрахункові поля й бізнес-логіка

Розрахункових полів і залежних формул немає. Автоматичний код є серверною
політикою створення, а не UI-формулою чи розрахунковим реквізитом.

### 9. Зберігання й API

Таблиця `ref_unit_of_measure` містить усі поля з розділу 2. Обов'язкові
обмеження й індекси:

- PK на `id`;
- UNIQUE на `code`;
- CHECK або еквівалентна application-перевірка формату коду для обох СУБД;
- індекс на `name`;
- індекс на `state`;
- `version` використовується для optimistic locking.

Послідовність кодів реалізується переносимою application/infrastructure-
політикою з однаковою поведінкою SQLite і PostgreSQL. Доменний код не визначає
тип СУБД. Міграції для обох СУБД додаються синхронно.

API:

- `GET /api/v1/catalogs/unit-of-measures` — сторінковий список і пошук;
- `GET /api/v1/catalogs/unit-of-measures/{id}` — картка елемента;
- `GET /api/v1/catalogs/unit-of-measures/picker` — дані форми вибору;
- `GET /api/v1/catalogs/unit-of-measures/new` — початковий стан нового елемента;
- `POST /api/v1/catalogs/unit-of-measures` — створення;
- `PUT /api/v1/catalogs/unit-of-measures/{id}` — зміна;
- `POST /api/v1/catalogs/unit-of-measures/{id}/mark-for-deletion` — помітка;
- `POST /api/v1/catalogs/unit-of-measures/{id}/restore` — відновлення.

API повертає стабільну помилку з кодом, українським повідомленням, деталями
валідації та correlation ID. Persistence-сутності через API не передаються.

### 10. Тести й критерії готовності

- Unit-тести: нормалізація й межі `name`/`shortName`, переходи станів,
  формат і ручна зміна коду.
- Application-тести: ініціалізація, створення, зміна, помітка, відновлення,
  idempotency та конфлікт версії.
- Integration-тести SQLite і PostgreSQL: міграції, унікальність коду,
  паралельне виділення кодів, сортування й пошук.
- API-тести: DTO, права, помилки валідації, correlation ID та optimistic locking.
- JavaFX-тести: список, елемент, вибір, початковий фокус, клавіші, редагування коду,
  права на створення та помітку на видалення.
- Наскрізний сценарій: створити одиницю, змінити її, вибрати в picker, помітити
  на видалення, переконатися у відсутності в новому виборі, відновити.

Паспорт можна перевести в `AGREED` лише після явного погодження користувачем.
Реалізація коду до цього не починається.
