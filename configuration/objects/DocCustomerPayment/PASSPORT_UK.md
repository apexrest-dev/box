# Паспорт документа «Оплата від покупця»

## 0. Стан паспорта

- Статус: `PROPOSED` — реалізовано в r2 за дорученням користувача 2026-11-08
  («подивися, зроби»); ревізія `r4` (розділ R4 нижче) — `PROPOSED`, реалізовано 2026-11-08 (Linear APE-57,
  F-SAL-07) без формального погодження. Потребує явного погодження для переведення в `AGREED`.
- Ревізія: `r4` (поверх `r2`).
- Розділ основного меню: `Документи`; панелі функцій `Продажі` і `Фінанси` (група «Банк», важливе).
- Залежності: `RefCounterparty`, `RefOrganization`, `RefContract`, `RefBankAccount`, `RefCashDesk`,
  `DocCustomerOrder`, `DocInvoiceForPayment`, `DocGoodsSale`, `RegCounterpartySettlement`, `RegCashBalance`,
  `DocBankStatement`.
- Аналог у 1С:УТ/УТП: Документ.ПриходныйКассовыйОрдер / ПоступлениеБезналичныхДенежныхСредств (спрощено).

## БЛОК A. СТРУКТУРА

Таблиця `doc_customer_payment`, сторінки 120/121. Поля: `customer_id`, `currency_code` = UAH,
`amount > 0`, `doc_comment`, `status`. Табличних частин немає.

### Статуси й життєвий цикл

`DRAFT -> POSTED` командою Post, `POSTED -> DRAFT` командою Unpost. У `POSTED`
шапка й рядки read-only (тригер). Фізичне видалення проведеного документа
заборонене. «Скопіювати (F9)» створює нову чернетку без номера, аудиту й рухів.
Повторне проведення атомарно замінює набір записів реєстратора.

## БЛОК B. UI

Форми: список (IR, сторінка 120) і документ (сторінка 121). Команди:
`Провести і закрити | Записати | Провести | Скасувати проведення | Скопіювати (F9) | Закрити`.

## БЛОК C. БІЗНЕС-ЛОГІКА

Проведення: `RegCounterpartySettlement` `RECEIVABLE` −amount. Переплата (від'ємний
залишок дебіторської заборгованості) заборонена. Рух каси/банку в r2 не формувався (знято в r4).


## R4. ДЖЕРЕЛО КОШТІВ, РАХУНОК НА ОПЛАТУ, РОЗШИФРОВКА ПЛАТЕЖУ (F-SAL-07, `PROPOSED`)

Дзеркало `DocSupplierPayment` R4. Аналог у 1С:УТ 11: Документ.ПоступлениеБезналичныхДенежныхСредств (вид «Оплата
від клієнта») / ПриходныйКассовыйОрдер з табличною частиною «Расшифровка платежа».

### R4.1. Нові поля шапки (`db/32_r4_customer_payment.sql`)

| Поле | Назва | Тип | Обов'язкове | Правило |
|---|---|---|---|---|
| `organizationId` | Організація | UUID | так | документ на підставі — організація підстави |
| `paymentForm` | Форма оплати | enum `BANK` / `CASH` | так | за замовчуванням `BANK` |
| `bankAccountId` | Банківський рахунок | `RefBankAccount` | для `BANK` | порожній → основний гривневий рахунок організації; лише UAH, тієї ж організації |
| `cashDeskId` | Каса | `RefCashDesk` | для `CASH` | порожня → перша гривнева каса організації; лише UAH, тієї ж організації |
| `contractId` | Договір | `RefContract` (`WITH_CUSTOMER`) | ні | порожній → договір рахунку / замовлення / підстави або єдиний діючий договір покупця |
| `customerOrderId` | Замовлення клієнта | `DocCustomerOrder` | ні | лише проведене, той самий покупець і організація; з рахунку, якщо рахунок за замовленням |
| `invoiceId` | Рахунок на оплату | `DocInvoiceForPayment` | ні | лише виданий (`ISSUED`), той самий покупець і організація |
| `baseDocType` / `baseDocId` | Документ-підстава | `DocGoodsSale` / `DocInvoiceForPayment` / `DocCustomerOrder` | ні | заповнюється введенням на підставі |
| `purpose` | Призначення платежу | String 500 | так (авто) | порожнє → «Оплата за товар згідно з <підстава / рахунок / замовлення>, <договір>» |

### R4.2. Таблична частина «Розшифровка платежу» (`doc_customer_payment_alloc`)

| Поле | Назва | Правило |
|---|---|---|
| `lineNumber` | № | 1… |
| `settlementDocType` / `settlementDocId` | Документ розрахунків | реєстратор позитивного руху `RECEIVABLE` (реалізація, коригування боргу тощо) |
| `settlementDocDate` | Дата боргу | дата руху документа розрахунків |
| `amount` | Сума | > 0; сума рядків ≤ сума оплати |

Заповнюється **лише проведенням** і видаляється скасуванням. Алгоритм `trade_cust_pay.allocate`:

1. сальдо дебіторки покупця за організацією на дату оплати (без самої оплати) розкладається на документи боргу за
   FIFO-припущенням — найновіші борги вважаються відкритими, найстаріші погашеними (так враховано ПКО, рядки
   виписок, коригування, повернення, які розшифровки не мають);
2. сума оплати розподіляється на відкриті документи в черговості: документ-підстава → реалізації замовлення
   оплати → решта за датою боргу (FIFO);
3. нерозподілений залишок допустимий (борг виник пізніше дати оплати) і показується в друці.

### R4.3. Проведення

```text
RegCashBalance:            period = occurredAt, місце = bankAccountId | cashDeskId, amount = +amount,
                           operation_kind = CUSTOMER_PAYMENT
RegCounterpartySettlement: counterparty = customerId, direction = RECEIVABLE, amount = −amount, organization
```

Контроль: переплата покупця в розрізі організації заборонена (`SETTLEMENT_NEGATIVE_BY_ORGANIZATION`; авансів ще
немає); скасування не може зробити залишок каси / рахунку від'ємним. API r2 `trade_ops.*_customer_payment` делегує
в `trade_cust_pay`.

### R4.4. Правило одного платежу

Як у `DocSupplierPayment` R4.3, вид операції рядка виписки — «Оплата від покупця» (`CUSTOMER_PAYMENT`):
автопідбір під час проведення виписки, прив'язаний рядок лише звіряє, `PAYMENT_ALREADY_IN_STATEMENT`,
`PAYMENT_LINKED_TO_STATEMENT`. Готівкова оплата від покупця — або ПКО «Оплата від покупця», або цей документ із
формою `CASH` (один платіж — один документ).

### R4.5. Рахунок на оплату: стан оплати

`trade_cust_pay.invoice_paid` = проведені оплати від покупця з `invoiceId` + проведені ПКО на підставі рахунку.
Стан (`payment_state`): `NOT_PAID` «Не оплачено», `PARTIAL` «Частково оплачено», `PAID` «Оплачено» — лише для
виданого рахунку; обчислюється, статус рахунку (`DRAFT/ISSUED/CANCELLED`) не змінюється. Список рахунків (320)
показує «Сплачено» й «Оплата», форма рахунку (321) — регіон «Оплати за рахунком».

### R4.6. Введення на підставі

| Звідки | Команда | Сума |
|---|---|---|
| Реалізація (проведена) | «Створити оплату від покупця» | min(сума реалізації, дебіторка організації) |
| Рахунок на оплату (виданий) | «Створити оплату від покупця» | min(сума рахунку − сплачено за рахунком, дебіторка) |
| Замовлення клієнта (проведене) | «Створити оплату від покупця» | min(сума замовлення − сплачено за замовленням, дебіторка) |

Нульова сума → `PAYMENT_NOTHING_TO_PAY`. Форма — `BANK`, якщо в організації є гривневий рахунок, інакше `CASH`.

### R4.7. Друковані форми (`trade_print.document_html`)

- `PAY_NOTICE` «Повідомлення про надходження оплати» — для `BANK`: платник (найменування, ЄДРПОУ, IBAN), отримувач
  (організація, IBAN, банк), сума цифрами й прописом, призначення, розшифровка платежу.
- `PAY_KO1` «Прибутковий касовий ордер (КО-1)» з квитанцією — для `CASH`.

### R4.8. UI і права

Сторінки 120/121; поля показуються за формою оплати; регіон «Розшифровка платежу». Права — схема «Роль: продажі або
каса» (Адміністратор, Менеджер з продажу, Касир). Список: форма оплати, рахунок / каса, розподілено, договір,
замовлення, рахунок, № виписки.
