# Паспорт довідника «Контрагенти»

## 0. Стан паспорта

- Статус: `AGREED`.
- Погодження: користувач явно погодив паспорт 2026-11-03.
- Ревізія: `r1`.
- Розділ основного меню: `Довідники`.
- Залежні паспорти: `RegCounterpartySettlement`, `DocGoodsReceipt`, `DocSupplierPayment`.

## БЛОК A. СТРУКТУРА

### 1. Ідентичність і призначення

| Параметр | Значення |
|---|---|
| Українська назва | Контрагенти |
| Технічне ім'я | `RefCounterparty` |
| Клас / ID | `Counterparty` / `CounterpartyId` |
| Таблиця | `ref_counterparty` |
| DTO / API | `CounterpartyDto` / `/api/v1/catalogs/counterparties` |

Простий неієрархічний довідник юридичних і фізичних осіб. У першій тестовій
ревізії роль постачальника/покупця не фіксується: один контрагент може брати
участь у різних операціях. Код — текстовий 9, автоматичний, унікальний і
редагований. Вид видалення — `MARK_FOR_DELETION`.

### 2. Поля

| Поле | Назва | Тип | Розмір | Обов'язкове | Редагування | БД |
|---|---|---|---|---|---|---|
| `id` | ID | UUID | — | так | ні | PK |
| `code` | Код | String | 9 | так | у `ACTIVE` | UNIQUE |
| `name` | Найменування | String | 255 | так | у `ACTIVE` | index |
| `state` | Стан | `CatalogState` | — | так | командами | index |
| `version` | Версія | long | — | так | ні | optimistic lock |
| `createdAt/createdBy` | Створено/автор | Instant/UUID | — | так | ні | audit |
| `updatedAt/updatedBy` | Змінено/автор | Instant/UUID | — | так | ні | audit |

### 3. Ієрархія і дочірні структури

Ієрархії, власника, груп, контактів, договорів і табличних частин у `r1` немає.

### 4. Стани, інваріанти та команди

Стани: `ACTIVE`, `MARKED_FOR_DELETION`. Найменування — 1–255 після `trim`.
Команди: `InitializeCounterparty`, `CreateCounterparty`, `UpdateCounterparty`,
`MarkCounterpartyForDeletion`, `RestoreCounterparty`.

## БЛОК B. UI

### 5. Форми

Три форми: список, елемент, вибір. Елемент: `code[25] | name[75]`. Список і
вибір: `Код`, `Найменування`, `Стан`. Візуальне оформлення буде замінене разом
зі спільною UI-бібліотекою.

### 6. Події введення

`code` і `name`: стандартні `INPUT_STARTED/INPUT_COMMITTED`, запис через
типізовані create/update-команди. Системні поля — `disabled`.

## БЛОК C. БІЗНЕС-ЛОГІКА

### 7. Сценарії

Ініціалізація, запис, помітка і відновлення повторюють серверний контракт
довідника. Помічений контрагент недоступний у новому документі, але залишається
у старих документах і рухах.

### 8. Розрахунки

Розрахункових полів немає.

### 9. Зберігання й API

Окрема таблиця, sequence та індекси SQLite/PostgreSQL. API list/picker/CRUD-state,
права `read/create/update/delete`, optimistic locking та аудит.

### 10. Тести й готовність

Інваріанти, унікальність коду, обидві СУБД, API/права/аудит, форми та використання
у документах і взаєморозрахунках.

## Доповнення r4 (APE-54, `PROPOSED`)

Для автопошуку контрагента в банківських виписках (`DocBankStatement`) додано необов'язкові реквізити
(`db/29_r4_bank_statements.sql`, тригер `ref_counterparty_req_biu`, форма 41):

| Поле | Назва | Тип | Розмір | Обов'язкове | Правило |
|---|---|---|---|---|---|
| `edrpou` | ЄДРПОУ / РНОКПП | String | 10 | ні | 8 цифр (юрособа) або 10 цифр (фізособа); `COUNTERPARTY_EDRPOU`; index |
| `iban` | IBAN | String | 34 | ні | нормалізація (без пробілів, верхній регістр), формат UA + 27 цифр і контрольна сума mod 97 (`trade_fin.check_iban`); index |

Унікальність не вимагається: автопошук бере лише однозначний активний збіг. Список (40) показує ЄДРПОУ й IBAN.
