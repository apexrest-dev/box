# QueryTable — інформаційна таблиця запиту

## 1. Призначення

`QueryTable` показує на формі елемента або документа результат типізованого серверного запиту. Рядки не є табличною частиною об'єкта, не входять до його агрегату і не зберігаються як стан форми.

Приклад у картці номенклатури:

```text
Залишки за складами
Склад | Залишок | Резерв | Доступно
```

Дані формує запит `GetProductStockByWarehouse(productId, atMoment)`.

## 2. Відмінність від табличної частини

| Властивість | Таблична частина | QueryTable |
|---|---|---|
| Належить агрегату | так | ні |
| Зберігається | так | ні |
| Редагується | за паспортом | ні |
| Записується разом з об'єктом | так | ні |
| Джерело | поля документа/довідника | серверний query handler |
| Формули | сервер під час зміни/запису | сервер під час запиту |

## 3. Серверний контракт

Паспорт задає конкретні:

- query name;
- request DTO;
- параметри та їх джерела;
- result-row DTO;
- стабільний row key, якщо потрібний вибір рядка;
- сортування, фільтри й paging;
- permission;
- помилки й порожній результат.

У метаданих не зберігається сирий SQL. JavaFX не виконує формул. Агент реалізує типізований application query і серверну read model.

## 4. Параметри

Параметр може отримувати значення з:

- ID відкритого об'єкта;
- версії або статусу;
- погодженого реквізиту форми;
- дати «станом на»;
- UI-фільтра самої таблиці;
- поточного користувача, якщо це серверний контекст.

Кожне джерело описується типізованим binding. Універсальні вирази або довільний Java/SQL-код у паспорті заборонені.

## 5. Колонки

Колонка має:

- англійське technical name для DTO;
- український caption для UI;
- дозволений тип із системи конфігуратора;
- формат і вирівнювання;
- ширину;
- sort/filter policy;
- ознаку calculated і опис серверного алгоритму;
- optional reference target для переходу до об'єкта.

Для колонки допустимі `STRING`, `NUMBER`, `DATE`, `DATETIME`, `BOOLEAN`, `CATALOG`, `DOCUMENT`. `TABLE_PART` і регістри не є значеннями клітинки.

## 6. Оновлення

За замовчуванням таблиця завантажується:

- під час відкриття форми;
- після натискання «Оновити»;
- після серверної команди, яку паспорт позначив як таку, що змінює її залежності;
- після commit параметра таблиці.

Автоматичного таймера немає. Значення є знімком останньої серверної відповіді.

Під час редагування основного об'єкта паспорт окремо визначає, чи query використовує збережений стан, чи дозволену серверну чернетку. JavaFX не змішує непідтверджені локальні значення із запитом неявно.

## 7. Поведінка UI

- клітинки read-only;
- дозволені виділення, копіювання, сортування, фільтри й paging;
- double-click або Enter можуть виконати тільки явно описану row action;
- reference-колонка може відкрити відповідний об'єкт за правом read;
- контекстне меню таблиці буде визначене разом із загальними правилами таблиць;
- повідомлення loading/empty/error є обов'язковими станами.

Вбудовані фільтри використовують стандартні поля й `INPUT_STARTED/INPUT_COMMITTED`.

## 8. Приклад паспорта

```text
QUERY_TABLE stockByWarehouse "Залишки за складами"
  query: GetProductStockByWarehouse
  refresh: ON_OPEN, MANUAL, AFTER_POSTING
  params:
    productId <- FORM_OBJECT_ID
    atMoment  <- FILTER.atMoment
  columns:
    warehouse "Склад"    CATALOG -> Catalog.Warehouse
    quantity  "Залишок"  NUMBER(15,3)
    reserved  "Резерв"   NUMBER(15,3)
    available "Доступно" NUMBER(15,3) calculated
```

## 9. Відкриті деталі

Компонент залежить від майбутніх погоджених правил `ENTITY_TABLE_UK.md`: клавіатура, контекстне меню, колонки, selection model, paging і row actions. До їх погодження не реалізовувати ці частини за припущеннями.
