# OwnedCatalogTable — вбудована таблиця підпорядкованого довідника

## 1. Назва і призначення

Технічна назва UI-виду:

```text
OWNED_CATALOG_TABLE
OwnedCatalogTable
```

Українська назва: **Вбудована таблиця підпорядкованого довідника**.

Компонент розміщується у формі збереженого елемента довідника-власника та показує елементи іншого довідника, для яких owner дорівнює ID відкритого елемента.

Приклад:

```text
Catalog.Product
    └── OwnedCatalogTable<ProductBarcode>
            owner: ProductBarcode.productId = currentProduct.id
```

## 2. Це не таблична частина і не QueryTable

| Властивість | Таблична частина | QueryTable | OwnedCatalogTable |
|---|---|---|---|
| Тип даних | дочірні рядки агрегату | read model запиту | інший довідник |
| Зберігання | разом із власником | не зберігається | кожний елемент окремо |
| Власний UUID | ID рядка | необов'язковий row key | UUID елемента довідника |
| Редагування | методами власника | заборонене | командами дочірнього довідника |
| Окрема картка | ні | ні | так |
| Окремий список/API | ні | query API | так |

## 3. Обов'язкова модель власника

Дочірній довідник у своєму паспорті явно визначає:

- `ownerRequired = true`;
- цільовий тип власника;
- типізоване owner-поле;
- правила архівації власника;
- заборону або окрему команду зміни власника.

У вбудованій таблиці owner:

- встановлюється з `FORM_OBJECT_ID`;
- не показується як редаговане поле;
- повторно перевіряється сервером;
- не може бути підмінений клієнтом.

## 4. Головне правило збереження

Створення або редагування дочірніх елементів дозволене тільки коли власник уже збережений і сервер повернув його persisted ID та version.

Для нового незбереженого власника:

- список показує порожній або disabled стан;
- `Додати`, `Редагувати`, `Видалити/Архівувати` заблоковані;
- UI показує пояснення «Спочатку запишіть елемент-власник».

Сам факт наявності UUID у локальній чернетці не вважається збереженим власником.

Сервер перед кожною mutation перевіряє існування owner у persistence. Для невідомого або ще не записаного UUID повертається стабільна помилка `OWNER_NOT_PERSISTED`.

## 5. Незалежні транзакції

Кожна дія дочірнього довідника є окремим серверним application-сценарієм і окремою транзакцією:

```text
CreateProductBarcode(productId, ...)
UpdateProductBarcode(barcodeId, version, ...)
ArchiveProductBarcode(barcodeId, version)
```

Після успішної відповіді дочірня зміна вже збережена.

Якщо користувач після цього:

- змінив поля основного елемента;
- не записав ці зміни;
- закрив форму або натиснув Escape,

вже записані дочірні елементи не відкочуються. UI не повинен створювати враження спільної транзакції.

## 6. Завантаження й оновлення

Список завантажується типізованим запитом дочірнього довідника з обов'язковим owner filter:

```text
GetProductBarcodes(productId, filter, sort, page)
```

Оновлення виконується:

- після відкриття збереженого власника;
- після create/update/archive дочірнього елемента;
- кнопкою «Оновити»;
- після повернення з картки дочірнього елемента.

Автоматичного таймера немає.

## 7. UI-команди

Підтримувані дії визначає паспорт дочірнього довідника:

- створити;
- відкрити;
- редагувати;
- архівувати/видалити;
- оновити список;
- optional copy, якщо він має предметний сенс.

За замовчуванням створення й редагування відкривають стандартну форму елемента дочірнього довідника. Inline-редагування не вводиться до погодження правил таблиць.

Owner у формі дочірнього елемента показується read-only або приховується згідно з паспортом.

## 8. Права

Компонент отримує capabilities сервера окремо для:

- читання дочірнього довідника;
- створення;
- редагування;
- архівації/видалення;
- відкриття картки.

Якщо немає `read`, таблиця не показує дані. Підтримувана, але заборонена дія видима й disabled. Незбережений owner блокує mutation незалежно від прав.

## 9. Конкурентність і видалення

- дочірній елемент має власну version;
- update/archive перевіряє optimistic locking;
- фізичне каскадне видалення разом із власником за замовчуванням заборонене;
- поведінка під час архівації власника визначається паспортом дочірнього довідника;
- зміна owner виконується лише окремою типізованою командою, якщо вона дозволена.

## 10. Опис у паспорті

```text
OWNED_CATALOG_TABLE barcodes "Штрих-коди"
  target: Catalog.ProductBarcode
  ownerField: product
  ownerSource: FORM_OBJECT_ID
  requirePersistedOwner: true
  editMode: CHILD_EDITOR
  refresh: ON_OPEN, AFTER_CHILD_COMMAND, MANUAL
  commands: CREATE, OPEN, UPDATE, ARCHIVE
```

## 11. Залежність від правил таблиць

Компонент використовує загальну таблицю і список простого довідника. Клавіатура, контекстне меню, selection model, колонки й paging остаточно визначаються після погодження `ENTITY_TABLE_UK.md` і `LIST_SIMPLE_CATALOG_UK.md`.

## 12. Обов'язкові тести

- незбережений owner: child mutation disabled у UI;
- підставлений UUID незбереженого owner: сервер повертає `OWNER_NOT_PERSISTED`;
- збережений owner: child create/update/archive працюють;
- список ніколи не показує записи іншого owner;
- незбережені зміни картки owner скасовано, але вже записаний child залишається;
- права child catalog правильно керують кнопками й серверними командами;
- optimistic locking дочірнього елемента;
- архівація owner відповідає погодженій child policy.
