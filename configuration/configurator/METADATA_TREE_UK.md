# Дерево метаданих і автоматичні каркаси об'єктів

## 1. Основне правило

Під час створення метаоб'єкта конфігуратор автоматично створює його DRAFT-ревізію, системні папки дерева й обов'язкові форми відповідно до виду.

Blueprint також створює системні реквізити з `SYSTEM_FIELDS_UK.md`. Вони показуються в тих самих папках структури, що й користувацькі поля, але мають locked definition.

Операція виконується application-сервісом в одній SQLite-транзакції та є ідемпотентною: повтор команди не створює дублікати папок або форм.

Системні папки:

- мають стабільний `systemKey`;
- показуються українською;
- не перейменовуються й не видаляються;
- можуть бути віртуальними вузлами дерева, якщо їм не потрібен окремий запис у БД.

## 2. Довідник

```text
Довідник «Номенклатура»
├── Загальне
├── Структура
│   ├── Реквізити
│   └── Табличні частини
├── UI
│   └── Форми
│       └── Форма списку
├── Події введення
├── Бізнес-логіка
├── Зберігання та API
├── Права і залежності
└── Тести та експорт
```

Обов'язкові форми:

| systemKey | Вид |
|---|---|
| `elementForm` | `EDITOR` |
| `listForm` | `LIST` |
| `pickerForm` | `PICKER` |

```text
Документ «Реалізація товарів»
├── Загальне

│   ├── Реквізити шапки
│   └── Табличні частини
│       └── <Таблична частина>
│           └── Реквізити рядка
├── Статуси та команди
├── UI
│   └── Форми
│       ├── Форма документа
│       ├── Форма списку
│       └── Форма вибору
├── Події введення
├── Бізнес-логіка
├── Проведення та рухи
├── Зберігання та API
├── Права і залежності
└── Тести та експорт
```

Обов'язкові форми:

| systemKey | Вид |
|---|---|
| `documentForm` | `EDITOR` |
| `listForm` | `LIST` |
| `pickerForm` | `PICKER` |

Під час створення табличної частини її дочірня системна папка «Реквізити рядка» з'являється автоматично.

## 4. Реєстр залишків

```text
Реєстр залишків
├── Загальне
├── Структура
│   ├── Виміри
│   └── Ресурси
├── UI
│   └── Форми
│       ├── Форма елемента
│       ├── Форма списку
│       └── Форма вибору
├── Джерела рухів
├── Бізнес-логіка
├── Підсумки та перерахунок
├── Зберігання та API
├── Права і залежності
└── Тести та експорт
```

Автоматично створюється тільки одна обов'язкова системна форма — `listForm`. Рухи не мають форми елемента або форми вибору та не редагуються користувачем напряму.

## 5. Реєстр відомостей

```text
Реєстр відомостей
├── Загальне
├── Структура
│   ├── Виміри
│   └── Ресурси
├── UI
│   └── Форми
│       └── Форма списку
├── Періодичність і режим запису
├── Бізнес-логіка
├── Зберігання та API
├── Права і залежності
└── Тести та експорт
```

Автоматично створюється тільки одна обов'язкова системна форма — `listForm`. Незалежні команди регістру відомостей можуть ініціюватися з неї; окремі форми елемента та вибору не створюються.

Під час створення будь-якого регістру blueprint одразу створює порожні системні папки `Виміри` і `Ресурси`. Окремі реквізити регістру на цьому етапі не підтримуються. Самі користувацькі поля автоматично не вигадуються: їх додають окремо через Insert. Системні поля period, recorder, lineNumber та аудит створюються лише відповідно до виду й режиму регістру.

## 6. Обов'язкові та додаткові форми

- системна форма має `required = true` і `isSystem = true`;
- її можна наповнювати UI-вузлами й змінювати український caption у дозволених межах;
- її не можна фізично видалити;
- додаткові форми дозволені й мають `required = false`;
- видалення додаткової DRAFT-форми не видаляє реквізити або команди, на які вона посилалася;
- погодження блокується, якщо обов'язкова форма відсутня або структурно невалідна.

## 7. Створення об'єкта

Insert у системній папці виду відкриває картку самого об'єкта. Вона не показує
майбутні реквізити, форми, статуси або рухи, але одразу містить початкові
параметри довідника чи документа. Для цих двох видів окремий вузол паспорта
після створення не додається. Паспорти регістрів залишаються окремими вузлами.

```text
Новий документ

Назва українською: [________________________]
Опис українською:  [________________________]
Технічне ім'я:     [створюється AI__________]

[Записати] [Скасувати]
```

`objectKind` уже визначений активною папкою дерева і не потребує поля вибору:

- Insert у «Довідники» — `CATALOG`;

## 8. Копіювання, видалення й відновлення

`F9` виконує «копіювати як новий». У поточній версії команда дозволена для:

- цілого метаоб'єкта — копіюються структура, форми, команди, правила, рухи,
  паспорти й залежності, але створюються нові UUID, revision 1 DRAFT і незалежні
  lineage реквізитів;
- користувацького реквізиту DRAFT — копіюються тип, властивості, policies та
  обидві події введення; системні реквізити не копіюються.

Self-reference скопійованого об'єкта перенаправляється на новий UUID. Перед
`Delete` конфігуратор формує звіт використань і каскадних наслідків:

- зовнішнє використання об'єкта блокує вилучення;
- блокувальне використання реквізиту правилом, рухом або owner-definition
  блокує видалення;
- звичайні вузли форми реквізиту можуть бути видалені разом із ним і явно
  перелічуються у звіті;
- системні реквізити й системні структурні вузли не видаляються.

Об'єкт лише з DRAFT переміщується до «Кошика DRAFT» і може бути відновлений.
Об'єкт із погодженою історією тільки архівується; його ревізії не видаляються.
- Insert у «Документи» — `DOCUMENT`;
- Insert у «Регістри відомостей» — `INFORMATION_REGISTER`;
- Insert у «Регістри залишків» — `BALANCE_REGISTER`.

```text
CreateMetadataObjectDraft(
  objectKind,
  displayNameUk,
  descriptionUk
)
        ↓
MetadataObject + ObjectRevision(DRAFT)
        ↓
specific passport row
        ↓
required cfg_form rows
        ↓
tree projection
```

AI technical name може бути сформовано після створення DRAFT. Системні ключі папок і форм від нього не залежать.

Для погодженого CREATE-flow technical name формується AI до команди «Записати», перевіряється application-сервісом і зберігається разом з об'єктом. Якщо AI тимчасово недоступний, окрема fallback-поведінка має бути погоджена до реалізації.

Після успішного запису картка закривається. Дерево перебудовується, новий об'єкт
стає активним, і лише тоді користувач бачить автоматично створені розділи,
system fields та required forms. Під час повторного відкриття картки команда
«Показати розгорнуте дерево» відкриває всю структуру об'єкта в окремому вікні.

Створення об'єкта не відкриває розширену картку всього паспорта. Подальше редагування виконується через вибір конкретних вузлів дерева.

## 8. Додавання вузлів

Кожна системна папка дозволяє лише доречні дочірні вузли:

- «Реквізити» — додати реквізит;
- «Табличні частини» — додати табличну частину;
- «Форми» — додати лише додаткову форму;
- «Бізнес-логіка» — додати правило;
- «Права і залежності» — додати permission або dependency.

UI не показує універсальну команду «Додати будь-що».

## 9. Перебудова дерева

Дерево є read model над нормалізованими таблицями конфігуратора. Його можна повністю перебудувати з `cfg_object`, `cfg_object_revision`, subtype passport, fields, table parts, forms, rules та dependencies.

Системні папки не є джерелом бізнес-даних і не потребують окремої універсальної таблиці довільних вузлів.

## 10. Вигляд TreeTableView

Основне дерево конфігуратора є read-only `TreeTableView` з двома обов'язковими колонками:

| Колонка | Зміст |
|---|---|
| `Назва` | українська назва вузла |
| `Тип` | тип об'єкта, реквізиту, форми або системного розділу |

Англійське technical name у дереві не показується. Воно доступне лише в картці елемента.

Приклади другої колонки:

```text
Реалізація товарів     Документ
Клієнт                 Довідник
Коментар               Строка
Товари                  Таблична частина
Форма документа         Форма елемента
Реквізити шапки         Системний розділ
```

### 10.1. Навігація і розгортання вузлів

- звичайні клавіші `↑` і `↓` переміщують виділення на попередній або наступний видимий рядок дерева;
- натискання мишкою на стандартний знак `+` біля папки розгортає її, на знак `−` — згортає;
- `Ctrl+↓` розгортає поточну папку або об'єкт, якщо вузол має дочірні елементи;
- `Ctrl+↑` згортає поточну розгорнуту папку або об'єкт;
- після розгортання чи згортання виділення залишається на поточному вузлі;
- для листового вузла без дочірніх елементів `Ctrl+↓` і `Ctrl+↑` нічого не змінюють і не показують помилку;
- ці комбінації не відкривають картку і не змінюють метадані.

## 11. Одна форма для нового й редагування

Для кожного редагованого виду вузла використовується одна й та сама картка у двох режимах:

```text
CREATE — новий елемент
EDIT   — редагування наявного
```

Наприклад, `FieldDefinitionEditor`:

- Insert відкриває його в режимі `CREATE`;
- F2 або команда «Редагувати» відкриває його в режимі `EDIT`.

Режим `CREATE`:

- показує порожні/default значення;
- знає тип майбутнього елемента і parent ID;
- не створює запис у SQLite до команди «Записати»;
- Escape/«Скасувати» закриває картку без запису.

Режим `EDIT`:

- завантажує елемент за UUID;
- містить version для optimistic locking;
- команда «Записати» виконує типізований update;
- скасування не змінює запис.

Після успішного запису дерево оновлюється і встановлює активним створений або змінений вузол.

## 12. Контекст Insert

Insert не відкриває універсальну форму. Поточний вузол визначає конкретну картку:

| Активний вузол | Результат Insert |
|---|---|
| `Довідники` | новий довідник |
| `Документи` | новий документ |
| `Реквізити шапки` | новий реквізит шапки |
| наявний реквізит | новий реквізит того самого parent |
| `Табличні частини` | нова таблична частина |
| наявна таблична частина | новий реквізит її рядка |
| `Форми` | нова додаткова форма |
| системна required форма | додавання UI-вузла виконується всередині її редактора |

Якщо поточний вузол не допускає створення, Insert споживається деревом і показує коротке пояснення або нічого не робить відповідно до погодженого стандарту клавіатури.

## 13. Відкриття наявного елемента

- F2 — відкрити картку в `EDIT`;
- double-click на редагованому вузлі — відкрити картку в `EDIT`;
- Enter на редагованому листовому вузлі — відкрити картку в `EDIT`;
- Enter/double-click на системній папці — розгорнути або згорнути;
- системні папки не мають форми редагування.
