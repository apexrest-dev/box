# Системні реквізити видів об'єктів

## 1. Основне правило

Під час створення DRAFT-ревізії blueprint автоматично створює системні реквізити відповідного виду об'єкта.

Системний реквізит:

- має стабільний `systemKey`;
- має `origin = SYSTEM`;
- не видаляється;
- не перейменовується;
- не змінює базовий тип, крім явно дозволеного параметра;
- може бути прив'язаний до UI-форми через звичайний `field_id`.

Форма не генерується автоматично. Користувач сам розміщує видимі системні поля в дереві форми, але validator перевіряє обов'язкові bindings.

## 2. Спільні технічні поля

Для змінюваних об'єктів:

| systemKey | Значення | UI policy |
|---|---|---|
| `id` | UUID | `HIDDEN` |
| `version` | optimistic-lock version | `HIDDEN` |
| `createdAt` | дата-тайм створення | `READ_ONLY_OPTIONAL` |
| `createdBy` | автор створення | `READ_ONLY_OPTIONAL` |
| `updatedAt` | дата-тайм зміни | `READ_ONLY_OPTIONAL` |
| `updatedBy` | автор зміни | `READ_ONLY_OPTIONAL` |

Приховане поле не з'являється у звичайному picker реквізитів форми. Read-only optional може бути додане до службової групи.

## 3. Довідник

| systemKey | Тип | UI policy |
|---|---|---|
| `code` | `STRING` | `REQUIRED_EDITOR` |
| `name` | `STRING` | `REQUIRED_EDITOR` |
| `state` | системний стан | `READ_ONLY_OPTIONAL` |

Вимоги:

- форма елемента містить `code` і `name`;
- форма списку містить `name`, а `code` — за паспортом;
- форма вибору містить `name`, а `code` — за паспортом.

Ієрархічний довідник додатково отримує системне типізоване поле `parent`. Довідник із власником отримує `owner` відповідно до свого паспорта.

## 4. Документ

| systemKey | Тип | UI policy |
|---|---|---|
| `number` | `STRING` | `REQUIRED_EDITOR` |
| `occurredAt` | `DATE` або `DATETIME` | `REQUIRED_EDITOR` |
| `status` | системний стан | `READ_ONLY_OPTIONAL` |
| `baseDocument` | `DOCUMENT`, якщо дозволено | `OPTIONAL` |

Тип `occurredAt` визначається параметром паспорта документа. Це єдиний дозволений type-parameter системного поля дати документа.

Вимоги:

- форма документа обов'язково містить `number` і `occurredAt`;
- форма списку містить `number`, `occurredAt` і `status`;
- форма вибору містить `number` та `occurredAt`;
- status редагується тільки object-командами, а не полем UI.

## 5. Таблична частина

Кожний рядок автоматично має:

| systemKey | Значення | UI policy |
|---|---|---|
| `lineId` | стабільний UUID рядка | `HIDDEN` |
| `lineNumber` | порядок рядка | `READ_ONLY_OPTIONAL` |

Вони не додаються користувачем до структури вручну.

## 6. Реєстр залишків

Системні поля руху:

| systemKey | Тип |
|---|---|
| `period` | `DATETIME` |
| `recorder` | `DOCUMENT` |
| `lineNumber` | `NUMBER` |

Форма списку за замовчуванням має bindings на period і recorder; lineNumber може бути прихованим.

## 7. Реєстр відомостей

- для періодичного: `period` типу `DATE` або `DATETIME` за паспортом;
- для recorder-managed: `recorder` і `lineNumber`;
- для independent: ID, version та аудит.

Форма списку обов'язково показує period, якщо регістр періодичний, і recorder, якщо він підпорядкований реєстратору.

## 8. Представлення в MetadataTree

```text
Документ «Реалізація товарів»
└── Структура
    └── Реквізити шапки
        ├── Номер       Строка       [системний]
        ├── Дата        Дата-тайм    [системний]
        ├── Статус      Стан         [системний]
        ├── Організація Довідник
        └── Клієнт      Довідник
```

У дереві системні поля можна позначати текстом або окремим presentation state. Decorative icons не є обов'язковими.

## 9. Редагування системного поля

F2 відкриває read-only або обмежену картку системного реквізиту:

- показує systemKey;
- показує українську й технічну назву;
- пояснює призначення;
- дозволяє лише параметри, прямо відкриті blueprint;
- не дозволяє видалення, зміну origin або несумісного типу.

Insert у папці реквізитів створює тільки користувацький реквізит і не дублює системні.

## 10. Валідація UI

Перед погодженням validator перевіряє:

- усі системні поля присутні у структурі;
- немає дубліката `systemKey`;
- required system fields прив'язані до відповідної форми;
- hidden fields не додані у звичайну форму;
- read-only поле не має editable UI-компонента;
- системна дата має погоджений DATE/DATETIME type;
- status не має `INPUT_COMMITTED` mutation.
