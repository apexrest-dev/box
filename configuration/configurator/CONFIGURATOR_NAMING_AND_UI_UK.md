# Двомовні назви та JavaFX UI конфігуратора

## 1. Ідентичність і назви

Кожна іменована сутність конфігуратора має щонайменше:

- `id` — стабільний UUID, єдина фактична ідентичність;
- `technicalName` — стабільне англійське ASCII-ім'я для Java, API, YAML, БД та агента;
- `displayNameUk` — єдина назва для списків, picker, пошуку й оператора;
- `descriptionUk` — український змістовний опис;
- aliases — попередні або додаткові українські назви.

Для об'єкта `objectKey` будується з виду та англійського імені:

```text
id:            4b9...
objectKind:    CATALOG
technicalName: RefCounterparty
displayNameUk: Контрагенти
objectKey:     Catalog.RefCounterparty
```

Для нових метаоб'єктів `technicalName` має обов'язковий префікс виду:

| Вид | Префікс | Приклад |
|---|---|---|
| довідник | `Ref` | `RefCounterparty` |
| документ | `Doc` | `DocGoodsReceipt` |
| регістр відомостей | `Reg` | `RegProductPrice` |
| регістр залишків | `Reg` | `RegStockBalance` |

Префікс застосовується тільки до метаоб'єкта. Реквізит має ім'я `Client`,
таблична частина — `Goods`, команда — `Post`. AI додає префікс автоматично.
Наявний legacy-об'єкт без префікса можна записати без примусового
перейменування; нове або змінене ім'я вже має відповідати правилу.

`technicalName` після першого погодження не змінюється. Зміна користувацького підпису не змінює UUID або технічні контракти.

Користувач вводить `displayNameUk` і `descriptionUk`. AI формує пропозицію `technicalName`, після чого конфігуратор перевіряє формат і унікальність. До погодження пропозицію можна повторно сформувати або виправити; після першого `AGREED` technical name незмінне.
Контрольоване перейменування змінює лише `displayNameUk`: попередня нормалізована
українська назва атомарно записується як активний alias. Назву не можна призначити
іншому активному об'єкту або реквізиту в тому самому контексті, доки вона є alias.
Повернення до попередньої назви дозволене власному об'єкту й деактивує зайвий alias.
Для реквізиту між ревізіями зберігається окремий стабільний `lineageId`; тому
technical name не можна обійти клонуванням погодженої ревізії з новими UUID.


У CREATE-картці нового метаоб'єкта немає дерева реквізитів і форм. Вона містить
українську назву, український опис, сформоване AI technical name і початкові
параметри виду. Параметри довідника та документа надалі редагуються в цій самій
картці. Для наявного об'єкта картка має команду «Показати розгорнуте дерево».
Вид об'єкта задається папкою, з якої натиснуто Insert.

## 2. Правила унікальності

- `technicalName` унікальне в межах виду об'єкта і проєкту;
- нормалізоване `displayNameUk` унікальне в тому самому контексті;
- технічні імена відповідають `[A-Z][A-Za-z0-9]*` (PascalCase);
- максимальна довжина `technicalName` — 48 ASCII-символів;
- точний збіг із ключовим або структурним SQL-іменем SQLite/PostgreSQL заборонений;
- українська назва не повинна бути порожньою;
- український alias не може неоднозначно вказувати на два активні об'єкти в одному контексті.

SQLite `NOCASE` не використовується як єдине джерело українського порівняння. Application-сервіс формує й зберігає нормалізовані пошукові значення.

Перед збереженням PascalCase перетворюється на SQL-кандидат: `CurrentDate` →
`CURRENT_DATE`. Якщо кандидат входить до забороненого переліку, запис
блокується. Зокрема заборонені `User`, `Order`, `Group`, `Table`, `Select`,
`Date`, `CurrentDate`, `PrimaryKey`, `Period`. Складені предметні імена
`UserAccount`, `OrderNumber`, `DocumentDate`, `PaymentPeriodType` дозволені.
Однакова перевірка працює для ручного введення, AI-пропозиції та application-команд.

## 2.1. Переносні фізичні імена SQLite/PostgreSQL

`technicalName` не використовується як SQL-ідентифікатор безпосередньо.
Воно є стабільним ім'ям Java, API, паспорта й агента. Генератор persistence-моделі
окремо створює фізичне lowercase `snake_case` ім'я з обов'язковим префіксом.

Таблиці:

| Вид | Шаблон | Приклад |
|---|---|---|
| довідник | `cat_<name без Ref>` | `cat_counterparty` |
| документ | `doc_<name без Doc>` | `doc_goods_receipt` |
| таблична частина | `doc_<document>__tp_<part>` | `doc_goods_receipt__tp_goods` |
| регістр відомостей | `ir_<name без Reg>` | `ir_product_price` |
| регістр залишків | `ar_<name без Reg>` | `ar_stock_balance` |

Колонки:

- системні колонки мають окремий затверджений словник;
- користувацький реквізит має шаблон `f_<name>`;
- зовнішній ключ має суфікс `_id`;
- не використовуються quoted mixed-case ідентифікатори на кшталт
  `"CustomerOrder"`, бо PostgreSQL вимагатиме точного quoting у кожному запиті;
- усі фізичні імена перевіряються за обмеженням PostgreSQL у 63 байти;
- якщо повне ім'я має до 63 ASCII-символів, воно використовується без зміни;
- якщо воно довше, SQL-генератор залишає перші 54 символи та додає `_` і
  перші 8 hex-символів стабільного хеша повної кваліфікованої адреси;
- однаковий паспорт завжди породжує однакове скорочене ім'я;
- після додавання префікса, суфікса чи хеша ім'я перевіряється на унікальність.

Через префікс нормальні метадані `RefUser`, `Order`, `Group` можуть існувати:
фізичні імена `cat_user`, `f_order`, `f_group` не збігаються з ключовими
словами. Генератор все одно перевіряє кінцеве фізичне ім'я за об'єднаним
переліком ключових слів SQLite і PostgreSQL.

Затверджені базові фізичні колонки:

- `id`, `code`, `name`, `state`, `version`;
- `created_at`, `created_by`, `updated_at`, `updated_by`;
- для документа: `document_number`, `occurred_at`, `document_status`;
- для руху: `movement_period`, `recorder_id`, `line_no`.

Не використовувати надто загальні фізичні колонки `user`, `order`, `group`,
`table`, `select`, `date`, `current_date`. Українські підписи та
PascalCase technical names при цьому не обмежуються цим списком.

## 2.2. Кваліфіковані адреси для пошуку й конструктора запитів

Для пошуку в коді, паспорті та майбутньому конструкторі запитів
використовується кваліфікована адреса:

```text
RefCounterparty.Name
RefProduct.Code
DocGoodsReceipt.Number
DocGoodsReceipt.Goods.Product
RegStockBalance.Warehouse
RegStockBalance.Quantity
```

Перший сегмент — ім'я метаоб'єкта з `Ref/Doc/Reg`; далі йдуть імена
реквізиту або табличної частини та її реквізиту.

Адреса потрібна для читабельності, пошуку, експорту й журналу змін.
Фактична ідентичність кожного сегмента — UUID. Конструктор запитів зберігає
типізоване дерево/AST із UUID, а не готовий SQL і не лише рядкову адресу.
SQL-генератор окремо розв'язує UUID у фізичні таблиці та колонки.
Український UI показує «Контрагенти → Найменування», а паспорт може
додатково показати `RefCounterparty.Name`. Зміна української назви не ламає запит.

## 3. Вибір у UI

У списках, таблицях, дереві конфігурації та полях вибору показується тільки українська назва:

```text
Контрагенти
Номенклатура
```

Контекстний пошук працює за:

- українською назвою;
- українськими aliases.

Пошук за `technicalName`, `objectKey` або UUID в операторському UI не виконується. Англійське поле показується тільки в картці елемента.

Після вибору UI зберігає типізований UUID, а не текст назви. Поле вибору використовує правила `docs/ui/REFERENCE_FIELD_UK.md` і `docs/ui/REFERENCE_PICKER_UK.md`.

## 4. Керування через AI

Оператор або AI може сформулювати запит українською:

```text
Додай реквізит «Клієнт» у документ «Реалізація товарів».
```

Перед командою application-сервіс виконує окремий read-only етап name resolution:

```text
українська назва
        ↓
пошук exact displayNameUk та українських aliases
        ↓
один MetadataObjectId/ObjectRevisionId
        ↓
типізована команда за UUID і version
```

Якщо знайдено нуль або кілька кандидатів, зміна не виконується: AI отримує список для уточнення. Після розв'язання агент бачить у паспорті UUID і `technicalName` та використовує їх у коді, API й БД. Імена не передаються безпосередньо в універсальну команду зміни поля.

## 5. Метадані як catalog-like об'єкти

Об'єкти конфігуратора — не доменні довідники Trade, але їхній UI використовує ті самі шаблони:

- форма списку;
- форма елемента;
- форма вибору для посилань;
- архівація або незмінні ревізії замість небезпечного фізичного видалення;
- optimistic locking, аудит і capabilities.

Перші catalog-like UI-об'єкти:

- проєкт конфігурації;
- метаоб'єкт;
- ревізія паспорта;
- реквізит;
- таблична частина;
- форма та вузол форми;
- подія поля;
- object-команда;
- бізнес-правило;
- залежність.

Їхні форми створюються явно в JavaFX. Конфігуратор не генерує власний UI з `cfg_form_node`; цей опис є даними паспорта майбутнього об'єкта Trade.

Порядок побудови дерева форми, початкові шаблони форми елемента, списку й
вибору та відмінність `OBJECT_LIST` від табличної частини описані у
[`FORM_EDITOR_UK.md`](FORM_EDITOR_UK.md).

## 6. Перший тестовий UI-об'єкт

Першим наскрізним об'єктом є `MetadataObject`:

| Реквізит | Компонент |
|---|---|
| UUID | read-only TextField |
| Вид об'єкта | typed ComboBox |
| Англійське ім'я | TextField, тільки в картці |
| Українська назва | TextField |
| Український опис | multiline TextField |
| Стан | read-only |
| Версія й аудит | read-only |

Форми:

- список із колонками «Українська назва», «Вид», «Стан»;
- редактор;
- picker, який повертає `MetadataObjectId`.

Саме цей об'єкт перевіряє:

- `EntityTable` та `EntityEditor`;
- TextField і typed ComboBox;
- ReferenceField/ReferencePicker у наступному об'єкті `ObjectRevision`;
- Insert, F2, F3, F4, Delete, F9 відповідно до capabilities;
- `INPUT_STARTED/INPUT_COMMITTED`;
- application/domain-валідацію та optimistic locking;
- український контекстний пошук і українські aliases;
- відсутність technical name у списку, picker і результатах пошуку.

## 7. Межа JavaFX і persistence

```text
JavaFX Configurator
      |
      | typed ApplicationFacade
      v
Application + Domain
      |
      | Repository ports
      v
trade-configurator.sqlite
```

JavaFX-контролери не читають SQLite напряму. Name resolution, унікальність, ревізії, валідація й запис виконуються application/domain шарами; SQL ізольований у persistence adapter.

## 8. Залежність від непогоджених таблиць

Детальні специфікації `EntityTable`, списків і табличних частин у головній UI-бібліотеці ще не погоджені. До реалізації відповідних екранів конфігуратора ці правила потрібно завершити. План не дозволяє вигадувати поведінку таблиць за припущеннями.

Конфігуратор є тестовим споживачем UI-бібліотеки, але не повинен приховано визначати глобальну поведінку компонентів. Нове загальне правило спочатку погоджується у відповідному файлі `docs/ui/`.
