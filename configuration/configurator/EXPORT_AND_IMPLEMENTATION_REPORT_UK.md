# Експорт паспорта та звіт реалізації

## Пакет export schema 2.2

Погоджена ревізія експортується як незмінний каталог. Поточна версія формату — `2.2`. Версія 2.2 додає окрему ознаку `codeEditable` для довідника. Версія 2.1 додала типізоване посилання на розділ системного довідника `Основне меню` та цільову форму `LIST`.

## Оновлення паспортів із конфігуратора

- `Оновити паспорт` експортує останню погоджену ревізію вибраного об'єкта до стабільного каталогу `exports/` у корені проєкту.
- після успішного погодження ревізії її паспорт оновлюється автоматично;
- `Оновити всі паспорти` експортує останні погоджені ревізії всіх активних об'єктів;
- DRAFT-об'єкт без погодженої ревізії не експортується й показується у переліку пропущених;
- файл `exports/index.json` атомарно оновлюється після пакетної операції та містить актуальні пакети, контрольні суми й причини пропусків;
- старі каталоги ревізій не перезаписуються як інша ревізія й залишаються доступними для історії.

## План реалізації для агента

Команда `Сформувати план реалізації` спочатку синхронізує погоджені паспорти, а потім атомарно записує:

- `exports/implementation-plan.json` — машиночитаний план;
- `exports/implementation-plan.md` — короткий план для оператора й агента.

Стан визначається порівнянням `revisionHash`, а не датою файлу:

- `NEW` — немає підтвердженої реалізації;
- `CHANGED` — hash актуальної погодженої ревізії відрізняється від реалізованого;
- `CURRENT` — реалізований hash відповідає актуальному паспорту;
- `REMOVED` — раніше реалізований об'єкт архівовано;
- `BLOCKED` — об'єкт не має погодженої або реалізованої ревізії чи не пройшов експорт.

До автоматичного завдання агенту входять лише `NEW`, `CHANGED` і `REMOVED`. `CURRENT` не змінюється, а `BLOCKED` потребує виправлення паспорта. Для кожного елемента план містить ID і номер ревізії, актуальний та реалізований hash, тип об'єкта й технічні імена залежностей.

Формування плану не змінює Java-код. Реалізація починається лише окремою явно дозволеною командою користувача.
Порядок полів і колекцій є стабільним, кодування — UTF-8, завершення рядків — LF.

Пакет містить:

- `passport.yaml` — повна машинна специфікація структури, UI і бізнес-правил;
- `dependencies.yaml` — окремий список залежностей;
- `passport.md` — короткий паспорт для людини;
- `implementation-task.md` — порядок реалізації для агента;
- `implementation-report.template.json` — шаблон зворотного звіту;
- `manifest.json` — версія схеми, hash ревізії та SHA-256 кожного файла.

`revisionHash` обчислюється зі стабільного переліку контрольних сум вихідних специфікацій.
Шаблон звіту містить цей hash, але сам не входить до обчислення `revisionHash`. Його власна
контрольна сума, як і суми решти файлів, міститься у manifest.

Після експорту файли пакета не змінюють. Заповнений звіт зберігають як окремий JSON-файл,
а не поверх `implementation-report.template.json`.

## Implementation report schema 1.0

Звіт містить:

- `reportSchemaVersion` — зараз `1.0`;
- `exportSchemaVersion`, `revisionId`, `sourceRevisionHash` — точна прив'язка до експорту;
- `gitCommit` — commit реалізації;
- `overallStatus` — `COMPLETE` або `PARTIAL`;
- `summaryUk` — український підсумок;
- `artifacts` — класи, API, міграції, UI, тести й документація;
- `checklist` — результат перевірки пунктів завдання.

Види артефактів: `JAVA_CLASS`, `API`, `MIGRATION`, `UI`, `TEST`, `DOCUMENTATION`.
Стани пунктів: `COMPLETE`, `PARTIAL`, `NOT_IMPLEMENTED`, `NOT_APPLICABLE`.

`COMPLETE` допускається лише тоді, коли звіт має артефакти й checklist та не містить
`PARTIAL` або `NOT_IMPLEMENTED`. `PARTIAL` зобов'язаний явно назвати хоча б один
незавершений пункт.

## Імпорт і зміна стану

Під час імпорту конфігуратор:

1. перевіряє обидві версії схем, UUID ревізії, commit і структуру звіту;
2. порівнює `sourceRevisionHash` з останнім зареєстрованим експортом;
3. читає `manifest.json` і повторно обчислює SHA-256 кожного файла пакета;
4. зберігає структуровані артефакти, checklist і шлях до звіту в SQLite;
5. для `PARTIAL` залишає ревізію в `AGREED`;
6. лише для повністю перевіреного `COMPLETE` атомарно переводить ревізію в `IMPLEMENTED`.

Ручне підтвердження з Markdown залишене для сумісності. Основний контрольований шлях —
кнопка «Імпортувати звіт агента» у вікні історії ревізій.
