# План реалізації конфігуратора паспортів

## Результат

Локальний одно-процесний JavaFX-конфігуратор із application/domain шарами та SQLite дозволяє створити чотири види паспортів, погодити незмінну ревізію та експортувати повний пакет завдання для агента. Кожна іменована сутність має UUID, англійське technical name та українську display name. Конфігуратор не генерує і не виконує runtime-код Trade.

## Етап 0. Архітектурні рішення

Підготувати ADR:

- окрема design-time SQLite-база;
- модулі app/ui/application/domain/persistence/ai/export без HTTP;
- формат і версія `passport.yaml`;
- незмінність погоджених ревізій;
- формат Markdown бізнес-правил;
- naming contract: український UI та англійські technical identifiers;
- безпечне українське AI name resolution у UUID;
- закритий enum десяти типів і правила допустимих контекстів;
- межа між описом UI та забороненою runtime-автогенерацією.
- єдиний спосіб реалізації JavaFX UI — типізований Java-код без FXML.

Погоджений початковий каркас: окремий модуль `configurator/`, Java 21, JavaFX, Maven, один локальний процес, SQLite, JDBC repository/persistence layer без Spring і версійні SQL-міграції. Точні версії залежностей фіксуються у `pom.xml` під час створення каркаса.

## Етап 1. База і доменне ядро

### База

- створити Flyway-міграції таблиць із `METADATA_DATABASE_SCHEMA_UK.md`;
- додати FK, CHECK, UNIQUE та індекси;
- додати normalized Ukrainian names та таблиці українських aliases;
- додати CHECK constraints для `ConfiguratorType`;
- перевірити чисте створення й оновлення попередньої версії;
- заборонити фізичне видалення погоджених ревізій application-рівнем.

### Application і domain

- реалізувати `ConfigurationProject`, `MetadataObject`, `ObjectRevision`;
- типізовані ID та enum;
- єдиний `ConfiguratorType` без API для додавання типів;
- команди create object, create/copy revision, update draft, validate, agree;
- optimistic locking і аудит;
- окремі typed specs чотирьох видів.
- read-only name resolver за українською назвою та українським alias;
- заборону mutation при неоднозначному resolution.

Критерій: можна створити DRAFT кожного виду, скопіювати ревізію і неможливо змінити AGREED.

## Етап 2. Реквізити, залежності та правила

- CRUD реквізитів і табличних частин тільки всередині DRAFT;
- обов'язкові English technical name та Ukrainian display name для всіх іменованих записів;
- fixed type picker: строка, число, дата, дата-тайм, булеан, довідник, документ, таблична частина, реєстр відомостей, реєстр залишків;
- типізований вибір цільового об'єкта;
- автоматичне створення/оновлення `cfg_object_dependency`;
- дві обов'язкові події кожного поля;
- object-команди;
- business rules, dependencies та examples;
- domain-валідація узгодженості типів і storage/value kinds.

Критерій: документ може вибрати погоджений довідник як тип реквізиту, а експорт бачить залежність.

## Етап 3. Готовність потрібних UI-компонентів

Для конфігуратора потрібні погоджені TextField, NumericField, Date/DateTimeField, Boolean CheckBox, ReferencePicker, input lifecycle та правила `METADATA_TREE_UK.md`.

`EntityTable` і списки основного Trade не блокують першу версію конфігуратора, тому що основне редагування виконується через дерево й картки.

## Етап 4. MetadataTree

Реалізувати read-only `TreeTableView` з колонками «Назва» і «Тип»:

- автоматичний blueprint системних папок;
- автоматичні system fields для кожного виду об'єкта;
- три required forms для довідника й документа: element/document, list і picker;
- одна required list form для реєстру залишків і реєстру відомостей;
- український пошук;
- tree picker, який повертає UUID;
- одна type-specific editor form у режимах `CREATE/EDIT`;
- Insert відкриває `CREATE`;
- F2/double-click відкриває `EDIT`;
- системна папка розгортається, але не редагується;
- inline-редагування дерева відсутнє;
- optimistic locking і структуровані application-помилки.

CREATE-картка кореневого метаоб'єкта не показує майбутню структуру, system fields
або required forms. Вона містить українську назву, український опис, AI technical
name і початкові параметри виду. Для довідника це ієрархія, підпорядкування,
власник, параметри коду та вид видалення; для документа — тип дати, нумерація,
документ-підстава і копіювання. Для довідника й документа окремий вузол паспорта
в дереві не створюється: ці параметри редагуються в картці самого об'єкта.
Окремий паспорт у дереві залишається для регістрів.

Форми пишуться явно. JavaFX викликає типізований ApplicationFacade й не використовує SQL або repositories.

Критерій: створений об'єкт має правильний автоматичний каркас і system fields, required forms не видаляються, CREATE не пише в SQLite до «Записати», а EDIT оновлює дерево після успішного запису.

## Етап 5. Картки властивостей метаданих

- картка метаоб'єкта;
- картка реквізиту;
- картка табличної частини;
- картка форми;
- картка UI-вузла;
- картка business rule;
- редактор посилання на metadata object;
- редактор Markdown-описів;
- відображення validation issues.

SQLite, AI та інші довгі операції виконуються поза JavaFX Application Thread. Остаточна валідація й статуси — в application/domain шарах.

## Етап 6. Чотири спеціалізовані редактори

### Довідник

- вид, ієрархія, групи, власник;
- базові поля;
- list/editor/picker;
- `NEW/SAVE`;
- архівація та розрахункові поля.

### Документ

- шапка, статуси й переходи;
- табличні частини;
- editor/list/picker;
- події всіх полів;
- `NEW/SAVE/POST/UNPOST/COPY`;
- розрахунки й mapping рухів.

### Реєстр залишків

- залишки та обороти з одного потоку рухів;
- dimensions/resources/attributes;
- recorder sources;
- read-only list;
- totals, snapshots, closed periods і rebuild.

### Інформаційний регістр

- periodic/non-periodic;
- recorder-managed/independent;
- dimensions/values/attributes;
- read-only або command-based list;
- latestAt та незалежні команди.

Критерій: кожен редактор зберігає тільки властиві його виду параметри й проходить свої validation rules.

## Етап 7. Редактор UI паспорта

- вбудований список форм;
- TreeTableView елементів вибраної форми;
- палітра UI-вузлів і панель властивостей;
- дерево вузлів форми;
- UI-вузол `QUERY_TABLE` із parameters, columns, refresh policy та row actions;
- UI-вузол `OWNED_CATALOG_TABLE` із target catalog, owner binding, persisted-owner gate та незалежними child-командами;
- додавання поля тільки з переліку структури;
- групи, вкладки, орієнтація, порядок і ширина;
- вибір стандартного компонента;
- перевірка відповідності data type/component;
- редактор колонок, фільтрів, команд і прав;
- preview дерева без генерації runtime-форми.

Детальний WYSIWYG не входить у MVP.

Реалізація `QueryTable` починається після погодження спільних правил `EntityTable`. Сирий SQL у паспорті, формули в JavaFX і persistence таблиця для результатів заборонені.

`OwnedCatalogTable` також залежить від правил таблиць. До їх погодження паспорт і експорт підтримуються, але inline-редагування не реалізується; create/update відкривають картку дочірнього довідника.

## Етап 8. Валідація й погодження

Валідатор має групи:

- identity;
- naming/aliases;
- structure;
- references/dependencies;
- UI completeness;
- input events;
- business rules;
- persistence/API;
- permissions;
- tests/examples.

Кожна проблема має code, severity, object path і повідомлення. `ERROR` блокує погодження, `WARNING` потребує явного підтвердження або погодженої політики.

Команда `AGREE` у транзакції повторно запускає валідацію, фіксує автора/час і створює hash канонічного представлення.

## Етап 9. Експорт завдання агенту

- канонічний serializer у versioned YAML;
- Markdown renderer окремо для чотирьох паспортів;
- dependency manifest;
- шаблон `implementation-task.md`;
- контрольні суми;
- атомарне створення каталогу експорту;
- повторний export тієї самої ревізії дає той самий зміст.

Завдання агенту містить:

- ID, revision і hash;
- англійські stable keys, українські назви та aliases;
- повний паспорт;
- порядок залежностей;
- вимогу повного вертикального зрізу;
- перелік очікуваних міграцій, API, UI і тестів;
- заборону змінювати погоджені правила припущеннями.

## Етап 10. Звіт реалізації

Після роботи агент формує звіт відповідності:

`Розділ паспорта | Реалізовані файли | Тести | Статус | Відхилення`.

Статус ревізії змінюється на `IMPLEMENTED` лише після перевірки:

- hash збігається;
- немає невиконаних обов'язкових пунктів;
- тести пройшли;
- відхилення погоджені новою ревізією або ADR.

## Етап 11. Тестування

- unit: інваріанти ревізій, типів, подій і правил;
- integration SQLite: міграції, FK, транзакції, optimistic locking;
- API: права, валідація, погодження й export;
- JavaFX: дерево, редактори, reference picker, unsaved state;
- naming: український exact/context search, українські aliases, неоднозначність і перейменування;
- UI: technical name видиме в картці, але відсутнє у списку, picker і пошуку;
- golden files: стабільність YAML/Markdown;
- end-to-end: створити довідник, використати його в документі, додати рух у регістр, погодити й експортувати.

## MVP

До першої робочої версії входять:

- один локальний проєкт і SQLite;
- один локальний адміністратор без екрана входу та повної системи авторизації;
- один JavaFX executable; application/domain/persistence межі без HTTP;
- український пошук, українські aliases, technical names у картці/експорті та AI resolver;
- `MetadataObject` як перший UI smoke object;
- опис `QueryTable` у паспорті та експорті; повний runtime-компонент після погодження правил таблиць;
- опис `OwnedCatalogTable`, блокування для незбереженого owner і перевірка незалежного збереження дочірніх елементів;
- чотири види паспортів;
- реквізити, табличні частини, посилання й залежності;
- дерево UI без WYSIWYG;
- події, object-команди й Markdown-правила;
- validate/agree/export;
- YAML, Markdown і implementation task.

Не входять:

- runtime-автогенерація форм або таблиць Trade;
- виконання формул із тексту;
- автоматичне написання Java-коду самим конфігуратором;
- спільне PostgreSQL-редагування;
- merge конфліктуючих ревізій;
- конструктор довільних звітів.

## Порядок першого наскрізного сценарію

1. Через catalog-like UI створити `MetadataObject`: `Counterparty / Контрагенти`.
2. Знайти його українським пошуком і вибрати через picker; переконатися, що `Counterparty` у пошуку не використовується.
3. Заповнити паспорт довідника та погодити його.
4. Створити `GoodsSale / Реалізація товарів`.
5. Вибрати `Контрагенти` для поля `client / Клієнт`; picker повертає UUID, а technical names потрапляють лише в паспорт.
6. Додати табличну частину `goods / Товари` та події її полів.
7. Створити `Stock / Товари на складах`.
8. Описати movement mapping документа.
9. Погодити всі ревізії у правильному порядку.
10. Експортувати завдання агенту й перевірити українські підписи, англійські technical identifiers, UUID, залежності та повноту пакета.
