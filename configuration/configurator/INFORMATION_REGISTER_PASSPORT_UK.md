# Паспорт інформаційного регістру в конфігураторі

## 1. Загальне

Таблиця `cfg_information_register_passport`:

`revision_id`, `periodicity`, `write_mode`, `period_precision`, `latest_slice_policy`, `deletion_policy`.

`periodicity`: `NON_PERIODIC` або `PERIODIC`.  
`write_mode`: `RECORDER_MANAGED` або `INDEPENDENT`.

Також задаються англійське technical name, українська display name, `Register.<Name>`, клас запису, таблиця, призначення та допустимі реєстратори. Кожний вимір і ресурс має обидві назви.

## 2. Структура

Поля поділяються на:

- виміри — утворюють бізнес-ключ;
- ресурси — збережені значення регістру.

Окремі додаткові реквізити регістру поки не підтримуються.

Для періодичного регістру обов'язкове `period/validFrom` із точною гранулярністю. Для підпорядкованого реєстратору додаються `recorder` і `lineNumber`.

Конфігуратор показує попередній unique constraint:

```text
NON_PERIODIC: dimensions
PERIODIC:     dimensions + period
RECORDER:     recorder + lineNumber
```

Остаточний ключ уточнюється паспортом.

## 3. UI

Одразу створюється одна обов'язкова системна форма списку. Окремі форми елемента та вибору не створюються.

- колонки періоду, вимірів і ресурсів;
- фільтри;
- перехід до реєстратора;
- зріз останніх на вибрану дату;
- експорт.

`RECORDER_MANAGED` завжди read-only.  
`INDEPENDENT` може дозволяти створення, зміну й видалення лише через явно описані типізовані серверні команди, ініційовані з форми списку. `RECORDER_MANAGED` завжди read-only.

Для кожного редагованого поля незалежного регістру потрібні `INPUT_STARTED/INPUT_COMMITTED`. Для read-only полів вони `DISABLED`.

## 4. Бізнес-логіка

Потрібно визначити:

- правило унікальності;
- поведінку повторного запису;
- алгоритм `latestAt`/зрізу останніх;
- включність меж періоду;
- часову зону;
- пріоритет записів в один момент;
- архівацію або видалення;
- аудит незалежних змін;
- заміну записів реєстратора під час повторного проведення.

Для calculated-значень задаються залежності, trigger, алгоритм, rounding, persistence і приклади.

Обов'язкові серверні сценарії:

- query list;
- query latestAt для періодичного виду;
- replaceByRecorder для recorder-managed;
- для independent — лише явно увімкнені `NEW/SAVE/DELETE_OR_ARCHIVE`.

## 5. Зберігання, API та готовність

Описуються FK, unique constraints, індекси за dimensions+period, DTO запитів, стабільне сортування, permissions, аудит і міграції SQLite/PostgreSQL.

Погодження блокується без виду періодичності, режиму запису, ключа, полів, списку, правил `latestAt` або незалежних команд і контрольних прикладів.
