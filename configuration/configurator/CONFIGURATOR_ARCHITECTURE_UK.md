# Архітектура конфігуратора паспортів

## 1. Межа системи

Конфігуратор працює лише під час проєктування:

```text
JavaFX Configurator
        |
        | application commands/queries
        v
Application + Domain
        |
        v
SQLite Persistence
        |
        v
trade-configurator.sqlite
        |
        | immutable export
        v
passport.yaml + passport.md + implementation-task.md
        |
        v
Agent -> static Trade implementation
```

Робочий сервер Trade не читає базу конфігуратора і не залежить від неї. Конфігуратор є одним локальним desktop-процесом без HTTP.

## 2. Пропоновані модулі

```text
configurator/
  app/           запуск і dependency composition
  ui/            JavaFX-форми та ViewModel
  application/   команди, queries і транзакції
  domain/        ревізії, інваріанти й валідація
  persistence/   SQLite repositories і міграції
  ai/            TechnicalNameGenerator
  export/        YAML/Markdown і пакет завдання
```

Для першої версії використовується один JavaFX executable і SQLite. Мережева версія розглядається лише коли потрібна одночасна робота кількох проєктувальників.

JavaFX-контролери не використовують JDBC, SQL або repositories. Вони викликають типізований application facade в тому самому процесі. Лише persistence adapter працює зі SQLite.

Увесь JavaFX-інтерфейс конфігуратора реалізується явним типізованим Java-кодом без FXML. Компонування екранів виконується класами форм, контейнерів і повторно використовуваних UI-компонентів. Це саме правило діє в основному проєкті Trade. Відмова від FXML не дозволяє переносити бізнес-логіку в UI: JavaFX-класи й надалі відповідають лише за представлення, локальний стан і виклик application facade.

## 3. Агрегати

Над паспортами об'єктів розташований агрегат `FrameworkRevision`. Він зберігає
глобальну архітектуру, серверні контракти, стандартні UI-компоненти, шаблони
чотирьох видів об'єктів і критерії якості. `ConfigurationRelease` є незмінним
знімком однієї погодженої ревізії каркаса та погоджених ревізій активних
об'єктів. Агент отримує саме реліз конфігурації, а не довільний набір актуальних
файлів робочого дерева.

- `ConfigurationProject` — конфігурація Trade та її параметри.
- `MetadataObject` — стабільна ідентичність об'єкта.
- `ObjectRevision` — повний паспорт конкретної версії.
- `FormDefinition` — дерево компонування однієї форми.
- `BusinessRuleDefinition` — опис перевірки, розрахунку або проведення.
- `ExportPackage` — незмінний результат погодженої ревізії.

`ObjectRevision` є основним aggregate root. Поля, табличні частини, UI, події й правила змінюються тільки через його application-команди.

## 4. Стани ревізії

```text
DRAFT --validate--> DRAFT(valid)
  |
  | agree
  v
AGREED --start implementation--> AGREED
  |
  | verified implementation report
  v
IMPLEMENTED
```

- валідація не змінює статус, а формує список помилок;
- `AGREED` і `IMPLEMENTED` не редагуються;
- команда «Створити нову ревізію» копіює погоджений паспорт у новий `DRAFT`;
- фізичне видалення погоджених ревізій заборонене.

## 5. Екран конфігуратора

Ліва панель — дерево конфігурації:

```text
Довідники
Документи
Регістри залишків
Інформаційні регістри
```

Види об'єктів і реквізитів вибираються тільки із закритого enum, описаного в `CONFIGURATOR_TYPE_SYSTEM_UK.md`.

Права панель — паспорт вибраної ревізії з послідовними вкладками:

1. **Загальне**.
2. **Структура**.
3. **UI**.
4. **Події введення**.
5. **Бізнес-логіка**.
6. **Зберігання та API**.
7. **Права і залежності**.
8. **Перевірка та експорт**.

Українські назви є єдиними підписами у списках, дереві, picker і пошуку. Англійські technical names відображаються тільки в картці елемента та використовуються агентом, у коді, БД й експорті. Детальні правила визначає `CONFIGURATOR_NAMING_AND_UI_UK.md`.

Шапка редактора містить назву, номер ревізії, статус і команди `Перевірити`, `Погодити`, `Експортувати`, `Створити нову ревізію`.

## 6. Редактор реквізиту

Для реквізиту конфігуратор показує:

- технічну й користувацьку назву;
- тип, довжину, precision/scale;
- обов'язковість і default;
- тип посилання та вибір цільового об'єкта;
- input/calculated/aggregate вид;
- stored/transient вид;
- редагованість;
- UI-компонент;
- `inputStarted` і `inputCommitted`;
- опис, валідації, розрахунок і приклади.

Посилання вибирається через форму вибору метаданих. Якщо цільова ревізія не реалізована, автоматично додається залежність із відповідним станом.

Редактори конфігуратора будуються на спільних JavaFX-компонентах Trade і є їх першим наскрізним тестовим застосуванням. Форми метаданих пишуться явно, без автогенерації з власної БД.

Внесення UI-елементів паспорта виконується окремим структурним редактором із `FORM_EDITOR_UK.md`: список форм, TreeTableView вузлів і панель властивостей.

## 7. Експорт

Пакет ревізії:

```text
exports/<object-key>/<revision>/
  passport.yaml
  passport.md
  dependencies.yaml
  implementation-task.md
  manifest.json
```

`passport.yaml` є машиночитаним знімком, `passport.md` — документом для погодження. `manifest.json` містить ID ревізії, час, версію схеми експорту та контрольні суми.

Експорт не є генерацією Java-коду. Агент отримує пакет, перевіряє його повноту та виконує повний вертикальний зріз відповідно до `OBJECT_PASSPORT_RULE_UK.md`.
