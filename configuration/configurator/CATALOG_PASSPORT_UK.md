# Паспорт довідника в конфігураторі

## 1. Загальне

Обов'язкові поля:

| Поле | Зміст |
|---|---|
| Англійське ім'я | стабільне `technicalName`, наприклад `Counterparty` |
| Українська назва | основна назва оператора, наприклад `Контрагенти` |
| Технічний ключ | `Catalog.<Name>` |
| Клас та ID-клас | цільові Java-імена |
| Таблиця та API | цільові технічні імена |
| Ієрархічний | якщо увімкнено, довідник має групи та системне поле parent |
| Власник | відсутній або типізоване посилання |
| Автонумерація коду | код автоматично формується системою |
| Ручне редагування коду | оператор може змінити запропонований або наявний код; якщо автонумерацію вимкнено, цей параметр обов'язково має бути ввімкнений |
| Унікальність коду | дублювання коду заборонене |
| Тип коду | TEXT зі збереженням початкових нулів або NUMBER |
| Загальна довжина коду | від 1 до 32 символів/цифр; початкове значення 32 |
| Вид видалення | фізичне DELETE або MARK_FOR_DELETION |
| Призначення | Markdown-опис |

Таблиця `cfg_catalog_passport`:

revision_id, hierarchical, subordinate, nullable owner_target_object_id,
code_auto_number, code_unique, code_type, code_length, deletion_policy.

## 2. Структура

Конфігуратор автоматично додає базові реквізити `id`, `code`, `name`, `state`, `version` і аудит. Вони видимі, але їх не можна видалити. Розмір і правила `code/name` уточнюються паспортом.

Кожний конкретний реквізит також має англійське технічне ім'я та українську назву. Редактор реквізитів має колонки:

`Порядок | Українська назва | Англійське ім'я | Тип | Обов'язкове | Посилання | Значення | Зберігання | UI`.

Права панель властивостей показує повний редактор `cfg_field`.

Ієрархічний довідник завжди має групи. Для нього додається parent, визначаються
допустимий батько, цикли, переміщення, видалення групи та поведінка дочірніх
елементів. Окремого режиму «ієрархічний без груп» немає. Для підпорядкованого
довідника ціль-власник вибирається з метаданих, після чого додається типізоване
системне поле owner.

Якщо потрібна дочірня колекція, вона оформлюється як таблична частина з власним списком полів та інваріантами.

## 3. UI

Обов'язкові форми:

- список простого або ієрархічного довідника;
- форма елемента;
- форма вибору.

Вкладка UI містить дерево форм, палітру стандартних компонентів і панель властивостей. Поле можна додати до форми вибором із реквізитів, а не ручним введенням шляху. Одна форма позначається default для кожного виду.

Паспорт фіксує:

- дерево груп і вкладок;
- компонент, caption, ширину, порядок і read-only;
- список колонок, фільтри й пошук;
- команди `Створити`, `Записати`, `Архівувати`, `Відновити`;
- права і клавіатуру;
- відхилення від стандартних UI-файлів.

Форма елемента може містити необов'язкові `QueryTable` за `docs/ui/QUERY_TABLE_UK.md`: пов'язані об'єкти, залишки, історію цін або інші read models. Вони не є реквізитами довідника й не зберігаються разом з ним.

Форма елемента може містити `OwnedCatalogTable` за `docs/ui/OWNED_CATALOG_TABLE_UK.md` для керування елементами підпорядкованого довідника. Створення/редагування доступне тільки після збереження власника; дочірні зміни записуються незалежно й не відкочуються разом із незбереженими змінами основної картки.

## 4. Події введення

Для кожного реквізиту обов'язкові `INPUT_STARTED` і `INPUT_COMMITTED`. Значення: `STANDARD`, `CUSTOM` або `DISABLED`.

Для `CUSTOM` необхідні:

- технічна назва обробника;
- опис поведінки UI;
- типізований query/command;
- очікувана серверна відповідь;
- помилки й приклади.

Посилальний реквізит завершує введення після вибору ID або явного очищення.

## 5. Бізнес-логіка

Обов'язкові object-команди:

- `NEW` — серверна ініціалізація нового елемента;
- `SAVE` — створення або запис змін.

Паспорт визначає одну стандартну команду видалення: DELETE або
MARK_FOR_DELETION. Для кожної команди описуються права, передумови, перевірка
посилань, optimistic locking, аудит і результат.

Розрахункове поле має правило з залежностями, trigger, алгоритмом, округленням, ручним override, зберіганням і контрольними прикладами.

## 6. Зберігання, API та готовність

Паспорт визначає FK, unique constraints, індекси, правила архівних посилань, DTO, команди, запити списку/елемента/вибору та помилки.

Валідація перед погодженням перевіряє:

- повноту базових і конкретних полів;
- коректність ієрархії та власника;
- існування цільових об'єктів посилань;
- наявність трьох форм;
- дві події кожного поля;
- `NEW/SAVE`;
- правила кожного calculated-поля;
- міграційні й тестові вимоги.
