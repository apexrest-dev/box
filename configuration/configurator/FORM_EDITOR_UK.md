# Редактор UI-форми в конфігураторі

## 1. Розділення структури й UI

Вкладка «Структура» визначає, які дані має об'єкт:

```text
Документ
├── реквізити шапки
└── табличні частини
    └── реквізити рядків
```

Вкладка «UI» визначає, як уже створені реквізити та частини розміщені на конкретній формі:

```text
Форма редактора
├── панелі й групи
├── поля, прив'язані до реквізитів
├── таблиці, прив'язані до табличних частин
└── кнопки, прив'язані до команд
```

UI-вузол не створює новий доменний реквізит і не копіює його тип або бізнес-правила.

## 2. Список форм

У вкладці UI спочатку показується вбудований список `cfg_form`:

```text
[Додати] [Відкрити] [Редагувати] [Видалити]

Форма документа       EDITOR
Список документів     LIST
Форма вибору          PICKER
```

Для кожного виду об'єкта валідатор перевіряє обов'язковий набір форм.

## 3. Редактор вибраної форми

Екран має три частини:

```text
┌──────────────┬──────────────────────────┬─────────────────────┐
│ Палітра      │ Дерево форми             │ Властивості вузла   │
│              │                          │                     │
│ Панель       │ HEADER                   │ Назва               │
│ Група        │ ├── actions              │ Caption             │
│ Поле         │ ├── numberAndDate        │ Орієнтація          │
│ Вкладки      │ CONTENT                  │ Ширина              │
│ Таблиця      │ └── goodsTab             │ Binding             │
│ Кнопка       │     └── goodsTable       │ Read-only           │
└──────────────┴──────────────────────────┴─────────────────────┘
```

| `TOTAL` | підсумкове значення таблиці з описаним джерелом або формулою |
Це структурний редактор на `TreeTableView`, а не WYSIWYG.

## 4. Початковий перелік UI-вузлів

| Код | Призначення |
|---|---|
| `PANEL` | велика область форми: header/content/footer |
| `GROUP` | горизонтальна або вертикальна група |
| `TAB_PANE` | контейнер вкладок |
| `TAB` | одна вкладка |
| `FIELD` | стандартний редактор реквізиту |
| `COMMAND_BAR` | панель команд |
| `COMMAND_BUTTON` | кнопка object-команди |
| `OBJECT_LIST` | список об'єктів форми списку або вибору |
| `TABLE_PART` | таблиця рядків табличної частини |
| `QUERY_TABLE` | інформаційна таблиця серверного запиту |
| `OWNED_CATALOG_TABLE` | вбудований список підпорядкованого довідника |
| `LABEL` | статичний український текст |
| `SPACER` | презентаційний проміжок |

Цей перелік є enum UI-вузлів, окремим від десяти типів даних.

`OBJECT_LIST` не є табличною частиною. Це UI-таблиця/read model, яка показує
об'єкти поточного довідника, документа або регістру. Для документа її
український підпис — «Список документів», для довідника — «Список елементів
довідника». Дочірні вузли `FIELD` визначають колонки списку й посилаються на
реквізити об'єкта. Додаткові обчислювані колонки описуються окремими
реквізитами моделі читання, а не реквізитами табличної частини.

## 5. Прив'язки

`FIELD`:

- користувач вибирає реквізит із passport structure picker;
- у `cfg_form_node.field_id` зберігається FK;
- component type визначається типом реквізиту;
- події введення беруться з `cfg_field_event`.

`TABLE_PART`:

- вибирає `cfg_table_part`;
- колонки створюються як UI-опис полів цієї частини;
- не створює нової табличної частини.

`COMMAND_BUTTON`:

- вибирає `cfg_object_command`;
- caption може перевизначити тільки текст кнопки;
- право і серверна команда не дублюються у вузлі.

`QUERY_TABLE` та `OWNED_CATALOG_TABLE` вибирають відповідні definitions із паспорта.

## 6. Початкові шаблони форм

Після створення метаоб'єкта конфігуратор автоматично створює не лише записи
форм, а й початкові дерева:

- форма елемента/документа — панель шапки, панель команд, група основних
  реквізитів і основна область;
- форма списку — панель команд і `OBJECT_LIST` із типовими колонками;
- форма вибору — read-only `OBJECT_LIST` із типовими колонками;
- форма регістру — єдина форма списку з `OBJECT_LIST`.

Шаблон є початковою заготовкою паспорта. Користувач може змінювати дерево,
додавати реквізити як колонки та розміщувати спеціальні UI-таблиці.
Табличні вузли є контейнерами. `OBJECT_LIST` і `TABLE_PART` приймають дочірні `FIELD` як колонки, `COMMAND_BAR` і `TOTAL`. Поле-колонка `TABLE_PART` має належати саме прив'язаній табличній частині; колонка `OBJECT_LIST` — шапці поточного об'єкта. `QUERY_TABLE` використовує колонки свого definition, але також може мати локальну панель команд і підсумки.

`TOTAL` зберігає український опис формули або джерела значення. Це специфікація для агента й серверної read model, а не формула, яку виконує конфігуратор.


## 7. Внесення елементів

Початкові команди редактора:

- «Додати дочірній»;
- «Додати поруч»;
- «Редагувати»;
- «Видалити»;
- «Вище»;
- «Нижче»;
- «Перемістити до групи».

Drag-and-drop можна додати пізніше. Для MVP достатньо команд, бо вони простіше валідуються і тестуються.

Під час додавання `FIELD` відкривається picker доступних реквізитів з українськими назвами. Technical name показується тільки в картці властивостей відповідно до загального naming rule.

Picker містить як користувацькі, так і дозволені системні реквізити. Hidden system fields не показуються. Required system fields мають бути розміщені відповідно до `SYSTEM_FIELDS_UK.md`.

Коди позиції підпису: `LEFT`, `TOP`, `HIDDEN`. Формат є presentation-only override і не змінює тип чи точність доменного реквізиту. `visible` керує початковою видимістю, а `spacing` задається від 0 до 100 умовних UI-одиниць.

## 8. Властивості вузла

Спільні:

- українська назва/caption;
- англійське technical name;
- parent;
- sort order;
- visible/read-only;
- width mode і width value;
- опис.

Контейнер:

- orientation;
- auto stretch;
- spacing;
- допустимі типи дочірніх вузлів.

Поле:

- binding на реквізит;
- standard component;
- label position;
- format;
- presentation-only override.

Таблиця:

- binding;
- висота;
- колонки;
- локальна command bar;
- empty/loading state.

## 9. Приклад документа

```text
EDITOR goodsSaleForm "Реалізація товарів"
  PANEL HEADER
    COMMAND_BAR actions
      COMMAND_BUTTON save    -> SAVE
      COMMAND_BUTTON post    -> POST
      COMMAND_BUTTON unpost  -> UNPOST
    GROUP numberAndDate HORIZONTAL
      FIELD number     -> header.number
      FIELD occurredAt -> header.occurredAt
      FIELD organization -> header.organization
    GROUP clientGroup HORIZONTAL
      FIELD client
      FIELD contract
  PANEL CONTENT
    TAB_PANE documentTabs
      TAB goods "Товари"
        TABLE_PART goodsTable -> tablePart.goods
      TAB movements "Рухи"
        QUERY_TABLE movementsTable
  PANEL FOOTER
    FIELD comment
```

## 10. Збереження

Форма і вузли належать DRAFT-ревізії паспорта. Кожна команда дерева зберігається в SQLite через application-сервіс.

Видалення вузла форми не видаляє:

- реквізит;
- табличну частину;
- object-команду;
- query definition;
- дочірній довідник.

Воно видаляє лише розміщення на цій формі.

## 11. Валідація

Погодження блокується, якщо:

- binding посилається на видалений або чужий елемент структури;
- тип вузла несумісний із binding;
- `TAB` знаходиться поза `TAB_PANE`;
- поле або кнопка має дочірні вузли;
- `TABLE_PART` посилається не на частину поточного документа;
- один form node має більше однієї binding;
- обов'язкова команда документа не представлена у погодженому UI без явного рішення;
- дерево має цикл або дубльований sort order.

## 12. Preview

MVP показує текстове дерево й панель властивостей. Візуальний preview JavaFX-форми може бути доданий пізніше, але не стає runtime-автогенерацією: остаточну форму Trade реалізує агент за погодженим паспортом.
