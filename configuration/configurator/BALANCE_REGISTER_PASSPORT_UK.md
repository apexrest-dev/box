# Паспорт реєстру залишків у конфігураторі

## 1. Загальне

Таблиця `cfg_balance_register_passport`:

`revision_id`, `register_kind`, `movement_model`, `negative_balance_policy`, `current_totals_enabled`, `snapshot_period`, `closed_period_policy`, `recalculation_policy`.

`register_kind` для цього типу завжди `BALANCE`; обороти отримуються запитом рухів за період, але окремого метатипу оборотного регістру немає.  
`movement_model`: signed resources або явний `INCOME/EXPENSE`.

Також задаються англійське technical name, українська display name, `Register.<Name>`, клас руху, таблиця, призначення і допустимі документи-реєстратори. Кожний вимір і ресурс має обидві назви.

## 2. Структура

Системні поля руху:

`id`, `period`, `recorder`, `lineNumber`.

Користувач додає:

- виміри;
- ресурси.

Окремі додаткові реквізити регістру поки не підтримуються.

Для ресурсу обов'язкові numeric-тип, precision/scale, знак/напрям, одиниця або валюта та rounding. Для виміру визначається участь у ключі підсумку й індексах.

## 3. UI

Одразу створюється одна обов'язкова системна форма списку. Окремі форми елемента та вибору не створюються; рухи не редагуються користувачем.

Конфігуратор описує:

- колонки period/recorder/dimensions/resources;
- фільтри й початковий період;
- групування та підсумки;
- перехід до документа-реєстратора;
- режим перегляду рухів, оборотів або залишків;
- експорт.

Усі редактори рухів мають стан `DISABLED`. Події введення описуються лише для презентаційних фільтрів і не змінюють записи регістру.

## 4. Бізнес-логіка

Для `BALANCE` обов'язково визначаються:

- формула залишку на момент;
- дозвіл від'ємних залишків;
- поточні підсумки;
- місячні знімки під час закриття;
- інвалідація пізніших знімків після зміни минулого періоду;
- контрольований перерахунок від дати зміни.

Для запиту оборотів визначаються межі періоду, групування і формула сумування рухів.

Обов'язкові серверні сценарії:

- атомарна заміна рухів реєстратора;
- сторнування/видалення рухів під час скасування проведення;
- запит рухів;
- запит оборотів;
- для залишкового регістру — запит залишку й rebuild підсумків.

Прямі UI-команди створення або зміни руху заборонені.

## 5. Залежності й джерела

Паспорт показує всі документи, що формують регістр, та їх погоджені movement mappings. Якщо документ ще не описав рухи, конфігуратор формує попередження.

## 6. Зберігання, API та готовність

Описуються таблиця рухів, похідні таблиці підсумків/знімків, FK, унікальність recorder+lineNumber, індекси запитів, queries і міграції SQLite/PostgreSQL.

Погодження потребує визначених вимірів, ресурсів, виду регістру, джерел рухів, алгоритмів залишку/обороту, політики закритого періоду, UI списку та контрольних прикладів.
